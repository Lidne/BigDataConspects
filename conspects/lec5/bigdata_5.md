# Конспект лекции: DWH, Lambda Architecture и Data Lake

Источник: транскрипция лекции `bigdata_5.txt` 

## 1. Повторение: концепция DWH / КХД

**DWH** - *Data Warehouse*, или **корпоративное хранилище данных / КХД**. Это одна из классических архитектур хранения и обработки данных, исторически сформировавшаяся в аналитических системах.

В лекции DWH описывается как архитектура, где данные проходят через несколько последовательных слоев: от сырых данных до готовых отчетов.

Классический подход DWH можно описать так:

```md
Источники данных
    ↓
RAW
    ↓
ODS
    ↓
DDS
    ↓
Datamart
    ↓
Report
    ↓
BI / аналитика / потребители
```

## 2. Основная идея DWH

DWH строится «слева направо»: сначала данные извлекаются из источников, затем раскладываются по слоям, очищаются, нормализуются, обогащаются и постепенно превращаются в удобные для бизнеса витрины и отчеты.

Преподаватель приводит метафору склада или шкафа:

* сначала все товары / вещи попадают в общее место;
* затем они раскладываются по категориям;
* потом из них собираются готовые наборы под конкретные задачи.

В DWH происходит то же самое:

* **RAW / ODS** - первичное размещение и базовая организация данных;
* **DDS** - детальная структурированная модель;
* **Datamart** - витрины под конкретные бизнес-задачи;
* **Report** - готовый слой для отчетности и BI.

## 3. Слои DWH

### 3.1. RAW layer

**RAW-слой** содержит данные в максимально исходном виде, близком к тому, как они пришли из источника.

Назначение RAW:

* сохранить исходные данные;
* иметь возможность переобработать данные при ошибках;
* зафиксировать историю загрузок;
* отделить прием данных от дальнейшей бизнес-логики.

RAW - это «точка входа» данных в хранилище.

### 3.2. ODS layer

**ODS** - *Operational Data Store*.

Этот слой используется для первичной обработки данных:

* приведение форматов;
* базовая очистка;
* дедубликация;
* унификация структур;
* подготовка к дальнейшей загрузке в детальную модель.

В транскрипции термин иногда распознан как `UDS`, но по контексту корректный термин - **ODS**.

### 3.3. DDS layer

**DDS** - *Detailed Data Store*.

Это слой детальных, уже хорошо структурированных данных. Здесь данные разложены по бизнес-сущностям и связям.

DDS можно воспринимать как «ядро» хранилища, из которого дальше строятся витрины.

Примеры сущностей в DDS:

* клиент;
* договор;
* продукт;
* операция;
* счет;
* транзакция;
* ценная бумага;
* заказ.

### 3.4. ADDS layer

Дополнительно может выделяться слой **ADDS** - *Access Data Detail Store*.

Он нужен для того, чтобы пользовательские запросы не мешали регламентным процессам.

Идея такая:

```md
DDS - используется регламентными ETL/ELT-процессами
ADDS - реплика DDS для пользовательского доступа
```

Если пользователи напрямую нагружают DDS тяжелыми запросами, это может мешать ночным загрузкам, пересчетам и другим регламентным процессам. Поэтому иногда делают отдельную копию DDS - ADDS.

### 3.5. Datamart layer

**Datamart** - слой витрин данных.

Витрина - это данные, подготовленные под конкретную бизнес-область или аналитическую задачу.

Примеры витрин:

* продажи;
* клиентский портфель;
* остатки на счетах;
* эффективность маркетинговых кампаний;
* финансовая отчетность;
* поведение пользователей.

Datamart уже ближе к бизнесу, чем DDS.

### 3.6. Report layer

**Report layer** - слой готовых отчетов.

Здесь данные уже подготовлены так, чтобы BI-инструменты могли быстро строить графики, таблицы, дашборды и регулярные отчеты.

К этому слою подключаются:

* Superset;
* DataLens;
* Metabase;
* другие BI-системы.

## 4. Альтернативные названия слоев

В разных компаниях слои могут называться по-разному.

Классический вариант:

```md
RAW → ODS → DDS → Datamart → Report
```

В других подходах могут использоваться названия:

```md
Staging → Core → Representation
```

В **Medallion Architecture**:

```md
Bronze → Silver → Gold → Platinum
```

Соответствие приблизительное:

| Классический DWH | Medallion Architecture | Смысл                                   |
| ---------------- | ---------------------- | --------------------------------------- |
| RAW              | Bronze                 | Сырые данные                            |
| ODS              | Silver                 | Очищенные и унифицированные данные      |
| DDS / Datamart   | Gold                   | Данные, готовые для аналитики           |
| Report           | Platinum               | Финальные отчеты и бизнес-представления |

## 5. DWH на Greenplum

Один из классических вариантов реализации DWH - построить все хранилище на **Greenplum**.

**Greenplum** - это MPP-СУБД, построенная на базе PostgreSQL-подобного движка.

MPP означает **Massively Parallel Processing**, то есть массивно-параллельную обработку.

Идея Greenplum:

* данные распределяются по нескольким дата-нодам;
* SQL-запрос разбивается на подзадачи;
* подзадачи параллельно выполняются на разных узлах;
* результат собирается обратно.

Greenplum одновременно выполняет две функции:

```md
Storage Layer + Compute Layer
```

То есть он и хранит данные, и выполняет вычисления.

## 6. Загрузка данных в Greenplum

Для загрузки данных из источников в Greenplum могут использоваться:

* **PXF** - Platform Extension Framework;
* **gpfdist** - инструмент Greenplum для параллельной загрузки файлов;
* доработки на стороне источников;
* внешние ETL-процессы;
* Apache Airflow как оркестратор.

В транскрипции `PXF` местами распознан как `IPXF`, но корректный термин - **PXF**.

## 7. Оркестрация DWH

Для управления расписанием загрузок используется **Apache Airflow**.

Пример регламента:

```md
01:00 - загрузка данных из источников в RAW
01:00–03:00 - обработка RAW → ODS
03:00–04:00 - обработка ODS → DDS
04:00–07:00 - построение Datamart
07:00–08:00 - построение Report
09:00 - менеджеры открывают BI и видят данные за T-1
```

**T-1** означает «текущая дата минус один день», то есть данные за вчера.

## 8. Resource Groups в Greenplum

Greenplum позволяет разделять ресурсы между разными типами нагрузки с помощью **resource groups**.

Например:

```md
60% ресурсов - регламентные загрузки
40% ресурсов - пользовательские запросы
```

Это нужно, чтобы пользовательские аналитические запросы не «съедали» ресурсы, необходимые для обязательных ночных загрузок.

Если пользовательская нагрузка превышает выделенный лимит, запросы могут вставать в очередь.

## 9. Преимущества простого DWH на Greenplum

Такой вариант архитектуры достаточно понятен и удобен:

* одна основная технология;
* SQL как основной язык обработки;
* хорошая совместимость с BI-инструментами;
* понятная слоистая структура;
* централизованное хранение;
* контроль качества данных на каждом этапе;
* подходит для относительно умеренных объемов данных.

В лекции упоминается, что для компаний с объемом данных примерно до **100 ТБ** Greenplum часто бывает достаточным решением.

## 10. Проблемы DWH «два в одном»

Главная проблема возникает из-за того, что Greenplum одновременно является и хранилищем, и вычислительным движком.

Проблемные сценарии:

```md
Много регламентных загрузок → страдают пользовательские запросы
Много пользовательских запросов → страдают регламентные загрузки
```

То есть аналитики и ETL-процессы начинают конкурировать за одни и те же ресурсы.

## 11. Проблема масштабирования Greenplum

Greenplum можно масштабировать горизонтально, добавляя новые ноды. Но это не всегда удобно.

При добавлении ноды обычно добавляются сразу:

* CPU;
* RAM;
* диски.

Проблема в том, что иногда нужны только вычислительные ресурсы, например CPU и RAM, но приходится покупать и диски, которые могут быть не нужны.

Это приводит к неполной утилизации ресурсов и росту стоимости владения.

## 12. Ограничения SQL-подхода

Еще одна проблема DWH на Greenplum - сложность реализации нетривиальной логики.

SQL хорошо подходит для:

* фильтрации;
* агрегации;
* join-операций;
* аналитических запросов;
* трансформаций табличных данных.

Но SQL хуже подходит для:

* сложной императивной логики;
* машинного обучения;
* обработки неструктурированных данных;
* сложных алгоритмов;
* работы с файлами, изображениями, видео;
* гибкой обработки событий.

В таких случаях приходится писать очень сложные SQL-запросы, которые трудно поддерживать.

## 13. Разделение нагрузки: Greenplum + ClickHouse

Одно из решений - разделить регламентную и пользовательскую нагрузку.

Идея:

```md
Greenplum - регламентные загрузки и тяжелая обработка
ClickHouse - пользовательские запросы, витрины и отчеты
```

Greenplum остается ядром обработки:

```md
RAW → ODS → DDS
```

А ClickHouse используется для:

```md
Datamart → Report → BI
```

## 14. CQRS-подход

Такое разделение похоже на принцип **CQRS** - *Command Query Responsibility Segregation*.

Смысл CQRS:

```md
Одна часть системы отвечает за запись и обработку данных
Другая часть системы отвечает за чтение и пользовательские запросы
```

В рассматриваемой архитектуре:

| Компонент  | Роль                                               |
| ---------- | -------------------------------------------------- |
| Greenplum  | Запись, регламентные загрузки, массивная обработка |
| ClickHouse | Быстрое чтение, аналитические запросы, BI          |
| Spark      | Интеграция с источниками и перекладывание данных   |
| Airflow    | Оркестрация                                        |
| Trino      | SQL-доступ к разным источникам                     |

## 15. ClickHouse как пользовательский слой

**ClickHouse** хорошо подходит для аналитических запросов на чтение.

Он используется для:

* витрин данных;
* report-слоя;
* быстрых аналитических запросов;
* подключения BI-инструментов;
* масштабирования пользовательской нагрузки.

Если бизнесу нужно больше мощности для аналитики, можно масштабировать ClickHouse, не трогая Greenplum.

Это снижает стоимость владения, потому что ресурсы масштабируются более адресно.

## 16. Роль Spark и Trino

**Apache Spark** используется как гибкий вычислительный инструмент.

Он может:

* подключаться к разным источникам;
* загружать данные;
* обрабатывать большие объемы;
* писать логику на Python, Java, Scala;
* работать как batch-движок;
* использоваться для ML-задач.

**Trino** предоставляет SQL-интерфейс к разным источникам данных.

С помощью Trino можно делать запросы к разным системам и, например, объединять данные из Greenplum и ClickHouse.

## 17. Преимущества разделенной архитектуры

Архитектура Greenplum + ClickHouse + Spark/Trino решает часть проблем простого DWH:

* регламентная и пользовательская нагрузка разделены;
* пользовательские запросы не мешают загрузкам;
* можно отдельно масштабировать Greenplum и ClickHouse;
* ClickHouse лучше справляется с чтением;
* Spark дает гибкость для интеграции и сложной обработки;
* повышается надежность;
* появляется возможность резервирования.

Но эта архитектура сложнее:

* больше технологий;
* сложнее эксплуатация;
* выше требования к команде;
* больше точек отказа;
* сложнее мониторинг и сопровождение.

## 18. Главная проблема DWH: задержка данных

Даже улучшенный DWH остается batch-ориентированным.

Главная проблема: данные долго идут от источника до отчета.

Пример:

```md
Событие произошло сейчас
↓
Ночью данные попали в RAW
↓
Потом обработались в ODS
↓
Потом попали в DDS
↓
Потом пересчитались витрины
↓
Потом обновился report-слой
↓
Потом BI увидел данные
```

В итоге от события до аналитики может пройти:

* несколько часов;
* сутки;
* двое суток;
* иногда больше.

Для многих бизнес-процессов это слишком медленно.

## 19. Пример бизнес-проблемы

Бизнес может хотеть знать состояние клиента прямо сейчас.

Например:

* сколько бонусов у клиента на карте;
* подходит ли клиент под акцию;
* можно ли сделать клиенту персональное предложение;
* актуален ли портфель клиента;
* какие операции он совершил сегодня.

Если данные обновляются только раз в сутки, возможна ситуация:

```md
Клиенту предложили акцию
↓
Клиент согласился
↓
Позже выяснилось, что данные были неактуальны
↓
Клиент на самом деле не подходил под условия
↓
Возникает негатив для клиента и компании
```

Это влияет на:

* клиентский опыт;
* доверие к бренду;
* эффективность маркетинга;
* финансовый результат.

## 20. Lambda Architecture

Для решения проблемы актуальности данных используется **Lambda Architecture**.

Lambda Architecture разделяет обработку на два слоя:

```md
Batch Layer - медленный, но точный
Streaming Layer - быстрый, но потенциально менее точный
```

Общая идея:

```md
Источники
    ↓
CDC
    ↓
Шина данных
    ↓              ↓
Batch Layer        Streaming Layer
    ↓              ↓
Точный отчет       Быстрый отчет
    ↓              ↓
        Объединение / выравнивание
```

## 21. CDC

**CDC** - *Change Data Capture*.

Это механизм захвата изменений в источниках данных.

CDC позволяет не ждать ночной выгрузки, а отслеживать изменения почти в реальном времени.

CDC может работать:

* через журналы транзакций СУБД;
* через инкрементальные выгрузки;
* через API;
* через коннекторы;
* через события.

Примеры технологий:

* Flink CDC;
* Debezium;
* Kafka Connect.

## 22. Шина данных

После CDC изменения попадают в шину данных.

Чаще всего используется **Apache Kafka**.

Шина становится общей входной точкой для двух слоев:

```md
Kafka → Batch Layer
Kafka → Streaming Layer
```

Данные в Kafka могут храниться ограниченное время, например несколько дней.

## 23. Batch Layer в Lambda Architecture

Batch Layer похож на классический DWH.

Он:

* работает по расписанию;
* обрабатывает большие объемы данных;
* строит полные агрегаты;
* исправляет неточности streaming-слоя;
* считается источником более точных данных.

Batch Layer медленнее, но надежнее с точки зрения полноты и качества.

## 24. Streaming Layer

Streaming Layer работает иначе.

Он запускается не по расписанию, а реагирует на появление новых данных в шине.

Принцип:

```md
Появилось новое событие
↓
Streaming Layer сразу его забрал
↓
Обновил промежуточное состояние
↓
Пересчитал небольшой агрегат
↓
Отправил результат в report/datamart
```

Streaming Layer работает с небольшими порциями данных:

* одно событие;
* несколько событий;
* микробатч;
* временное окно.

## 25. Оконная обработка

Streaming Layer часто работает с временными окнами.

Например:

```md
Окно агрегации = 15 минут
```

В течение этого окна система может:

* собирать события;
* дедублицировать их;
* считать агрегаты;
* обновлять состояние.

Проблема: если дубль пришел позже окна, например через 16 минут, streaming-слой может не распознать его как дубль.

Поэтому streaming-результаты быстрые, но не всегда идеально точные.

## 26. Выравнивание batch и streaming

В Lambda Architecture batch-слой считается более точным.

Поэтому после batch-пересчета может выполняться корректировка streaming-результатов.

Принцип:

```md
Streaming Layer дает быстрый предварительный результат
Batch Layer позже пересчитывает точно
Batch Layer корректирует итоговые данные
```

## 27. Где использовать streaming, а где batch

Streaming подходит для:

* текущего состояния клиента;
* оперативных акций;
* near real-time мониторинга;
* быстрых уведомлений;
* актуального портфеля клиента;
* событийной аналитики;
* оперативных дашбордов.

Batch подходит для:

* финансовой отчетности;
* закрытия дня;
* сверок;
* регламентных отчетов;
* точных агрегатов;
* исторической аналитики;
* юридически значимых отчетов.

## 28. Единая кодовая база

Важная рекомендация из лекции: batch и streaming желательно строить на единой кодовой базе.

То есть один и тот же код должен уметь запускаться в двух режимах:

```md
mode = batch
mode = streaming
```

Преимущество:

* изменения в бизнес-логике вносятся один раз;
* меньше расхождений между слоями;
* проще сопровождение;
* ниже риск ошибок.

Если сделать две разные реализации, придется поддерживать две разные логики, что сильно увеличивает стоимость сопровождения.

## 29. Технологический стек Lambda Architecture

Возможные технологии:

| Задача                       | Технологии                                   |
| ---------------------------- | -------------------------------------------- |
| CDC                          | Flink CDC, Debezium, Kafka Connect           |
| Шина данных                  | Kafka                                        |
| Batch processing             | Spark, Flink                                 |
| Streaming processing         | Flink, Spark Structured Streaming            |
| Холодное хранилище           | Hadoop HDFS, YTsaurus, S3-compatible storage |
| Report layer                 | ClickHouse                                   |
| SQL-доступ                   | Trino                                        |
| BI                           | Superset, DataLens                           |
| In-memory state              | Redis, Dragonfly, Valkey                     |
| Колоночные / NoSQL-хранилища | Cassandra, ScyllaDB, Aerospike, HBase        |

В транскрипции некоторые названия были искажены: `Ready` → **Redis**, `Walkie` → **Valkey**, `Scilla` → **ScyllaDB**, `Trina` → **Trino**.

## 30. Преимущества Lambda Architecture

Lambda Architecture дает:

* более актуальные данные;
* near real-time обработку;
* резервный batch-контур;
* возможность корректировать streaming-результаты;
* повышение надежности;
* разделение быстрых и точных сценариев;
* поддержку критичных бизнес-процессов.

## 31. Недостатки Lambda Architecture

Главный недостаток - сложность.

Проблемы:

* больше компонентов;
* больше технологий;
* сложнее инфраструктура;
* дороже сопровождение;
* сложнее мониторинг;
* выше требования к компетенциям;
* сложнее отладка;
* нужно синхронизировать batch и streaming;
* требуется аккуратно проектировать состояние и окна.

Lambda Architecture решает проблему актуальности данных, но сильно усложняет систему.

## 32. Преимущества DWH

DWH дает следующие преимущества:

### Централизованное хранение

Все данные находятся в единой архитектуре и организованы по слоям.

### Историчность

Можно хранить историю изменений данных.

### Единая модель данных

Данные приводятся к единой структуре, что повышает качество аналитики.

### Поддержка BI

DWH хорошо подходит для отчетности, дашбордов и регулярной бизнес-аналитики.

### Разделение операционной и аналитической нагрузки

Операционные системы не нагружаются аналитическими запросами.

### Контроль качества данных

Data Quality-проверки можно выполнять на разных этапах:

```md
RAW → ODS → DDS → Datamart → Report
```

Если ошибка появилась в RAW, ее можно обнаружить до того, как она попадет в витрины.

## 33. Недостатки DWH

### Сложность реализации

Даже простой DWH требует:

* архитектуры слоев;
* ETL/ELT-процессов;
* модели данных;
* оркестрации;
* мониторинга;
* контроля качества.

### Задержка актуализации

Данные могут обновляться за:

* T-1;
* T-2;
* неделю назад;
* месяц назад.

Это плохо для сценариев, где данные нужны «здесь и сейчас».

### Ограничения для неструктурированных данных

DWH плохо подходит для хранения и обработки:

* видео;
* изображений;
* бинарных файлов;
* логов в произвольном формате;
* полуструктурированных документов.

### Трудоемкое подключение новых источников

Новый источник нужно провести через все слои:

```md
RAW → ODS → DDS → Datamart → Report
```

Это долго и дорого.

### Сложность изменения модели

Если ошибка была допущена в начале проектирования, например в ключах или модели сущностей, исправлять ее придется во всех слоях.

### Лавинообразное распространение ошибок

Если ошибка появилась в ETL между RAW и ODS, она может дальше распространиться на:

```md
ODS → DDS → Datamart → Report
```

Поэтому нужны высокие стандарты разработки, тестирования и Data Quality.

### Плохая поддержка ad hoc-запросов

DWH плохо подходит для быстрых нерегламентных исследований, особенно если аналитикам нужен доступ к сырым данным.

## 34. Data Lake

**Data Lake** - архитектура, которая возникла как попытка решить часть проблем DWH.

Главная идея Data Lake:

```md
Сначала загружаем все данные как есть,
а потом обрабатываем их по мере необходимости.
```

Если DWH чаще соответствует подходу **ETL**:

```md
Extract → Transform → Load
```

то Data Lake ближе к подходу **ELT**:

```md
Extract → Load → Transform
```

## 35. Основная идея Data Lake

В Data Lake данные из разных источников быстро загружаются в большое дешевое хранилище.

Туда можно складывать:

* структурированные данные;
* полуструктурированные данные;
* неструктурированные данные;
* файлы;
* логи;
* JSON;
* Parquet;
* Avro;
* изображения;
* видео;
* бинарные объекты.

Главная цель - собрать как можно больше данных в одном месте, даже если прямо сейчас непонятно, понадобятся они или нет.

## 36. Архитектура Data Lake

Упрощенно:

```md
Источники данных
    ↓
Compute Layer для загрузки
    ↓
Основной Storage Layer Data Lake
    ↓
Compute Layer для обработки под бизнес
    ↓
BI Storage / витрины
    ↓
BI-инструменты
```

Дополнительно есть отдельный compute-контур для:

* аналитиков;
* data scientists;
* ML-инженеров;
* ad hoc-исследований.

## 37. Отличие Data Lake от DWH

DWH строится от природы данных:

```md
Сначала проектируем слои и модель,
потом раскладываем данные,
потом строим витрины.
```

Data Lake строится от потребности:

```md
Сначала загружаем все,
потом под конкретный бизнес-запрос достаем и обрабатываем нужное.
```

## 38. Data Lake и ad hoc-аналитика

Data Lake хорошо подходит для ad hoc-запросов.

Если аналитик хочет быстро проверить гипотезу, ему не нужно ждать, пока источник будет полноценно встроен в DWH.

Данные уже лежат в озере, и их можно обработать напрямую.

Это удобно для:

* исследований;
* ML;
* проверки гипотез;
* первичного анализа;
* нестандартных задач;
* работы с сырыми данными.

## 39. Data Lake и машинное обучение

Data Lake хорошо подходит для ML, потому что модели часто требуют:

* больших объемов данных;
* сырых данных;
* исторических данных;
* полуструктурированных данных;
* неструктурированных данных;
* файловых форматов;
* гибкой обработки.

В DWH такие данные часто недоступны или сильно преобразованы. В Data Lake они сохраняются ближе к исходному виду.

## 40. Технологический стек Data Lake

В Data Lake могут использоваться разные инструменты.

### Хранилище

Основное требование: хранилище должно быть дешевым, масштабируемым и уметь хранить любые данные.

Возможные варианты:

* Hadoop HDFS;
* YTsaurus;
* S3-compatible storage;
* Ozone;
* Ceph.

### Табличный слой поверх файлов

Для структурирования файлов можно использовать:

* Apache Iceberg;
* Delta Lake;
* Apache Hudi.

В лекции упоминается **Iceberg** как способ организовать файлы в табличную форму через метахранилище.

### Compute

Для обработки данных:

* Apache Spark;
* Apache Flink;
* Trino;
* StarRocks.

В транскрипции `StarOx` следует читать как **StarRocks**.

### BI-слой

Так как BI-инструменты не умеют удобно работать с полностью сырым Data Lake, под них обычно готовят отдельное структурированное хранилище, например:

* ClickHouse;
* Greenplum;
* PostgreSQL;
* другие аналитические СУБД.

BI-инструменты:

* Superset;
* Metabase;
* DataLens.

## 41. Преимущества Data Lake

### Хранение любых типов данных

Data Lake может хранить:

* таблицы;
* JSON;
* XML;
* логи;
* изображения;
* видео;
* бинарные файлы;
* сырые выгрузки;
* архивы.

### Низкая стоимость хранения

Data Lake обычно строится на дешевых распределенных файловых или объектных хранилищах.

Это дешевле, чем хранить все данные во множестве структурированных слоев DWH.

### Быстрое появление данных

Данные можно быстро загрузить в озеро без долгого проектирования всей модели.

Это особенно важно, когда бизнесу нужно быстро начать анализ.

### Масштабируемость

Data Lake можно масштабировать под огромные объемы данных.

Он подходит для хранения данных, которые:

* нужны сейчас;
* могут понадобиться позже;
* возможно, никогда не понадобятся, но стоят дешево.

### Гибкость инструментов

Можно выбирать разные инструменты под разные задачи:

* Spark для больших batch-обработок;
* Flink для streaming;
* Trino для SQL-запросов;
* StarRocks для аналитики;
* ML-инструменты для обучения моделей.

### Удобство для ML и Data Science

ML-команды получают доступ к сырым и разнообразным данным, что полезно для обучения моделей.

## 42. Недостатки Data Lake

### Риск хаоса

Главная проблема Data Lake - он может превратиться в «файловую помойку».

Если нет строгого управления, становится непонятно:

* какие данные где лежат;
* кто их загрузил;
* какие данные актуальны;
* какие данные качественные;
* какие данные можно использовать;
* какие данные содержат чувствительную информацию.

### Сложный поиск данных

В DWH структура задается слоями и моделью.

В Data Lake структура часто ближе к файловой системе. Если нет каталога данных и метаданных, поиск становится очень сложным.

### Низкое качество данных

Так как данные загружаются «как есть», они могут содержать:

* ошибки;
* дубли;
* пропуски;
* некорректные форматы;
* неоднозначные поля;
* устаревшие версии;
* неполные записи.

В DWH качество контролируется по слоям. В Data Lake это нужно организовывать отдельно.

### Высокий порог входа

Для работы с Data Lake часто недостаточно SQL.

Нужно знать:

* Spark;
* PySpark;
* Scala / Java;
* файловые форматы;
* партиционирование;
* распределенную обработку;
* особенности хранения;
* работу с метаданными.

### Низкая производительность простых запросов

Если данные не структурированы, не отсортированы, не партиционированы и не подготовлены, даже простой запрос может быть тяжелым.

Аналитику может потребоваться самостоятельно:

* найти данные;
* понять формат;
* очистить данные;
* провалидировать данные;
* объединить разные источники;
* оптимизировать обработку.

### Риски безопасности

Data Lake сложно контролировать с точки зрения безопасности.

В нем могут оказаться:

* персональные данные;
* банковская тайна;
* коммерческая тайна;
* чувствительные клиентские данные;
* технические логи;
* документы с ограниченным доступом.

Если нет классификации и governance-процессов, становится трудно понять, кому можно давать доступ.

## 43. DWH vs Data Lake

| Критерий                     | DWH                                         | Data Lake                             |
| ---------------------------- | ------------------------------------------- | ------------------------------------- |

| Данные                       | В основном структурированные                | Любые                                 |
| Модель                       | Жесткая, заранее спроектированная           | Гибкая, часто поздняя                 |
| Качество данных              | Контролируется по слоям                     | Требует отдельного governance         |
| BI                           | Очень удобно                                | Обычно нужен отдельный слой           |
| ML                           | Ограниченно                                 | Хорошо подходит                       |
| Ad hoc                       | Ограниченно                                 | Удобнее                               |
| Стоимость хранения           | Выше                                        | Ниже                                  |

## 44. Главное сравнение DWH, Lambda и Data Lake

| Архитектура         | Что решает                                        | Главная проблема                                |
| ------------------- | ------------------------------------------------- | ----------------------------------------------- |
| DWH                 | Качественная централизованная отчетность          | Медленная поставка данных, сложность изменений  |
| DWH + ClickHouse    | Разделение регламента и пользовательской нагрузки | Усложнение инфраструктуры                       |
| Lambda Architecture | Актуальные данные почти в реальном времени        | Очень высокая сложность                         |
| Data Lake           | Быстрая загрузка любых данных и гибкий анализ     | Риск хаоса, низкое качество, сложный governance |

## 45. Ключевые выводы лекции

1. **DWH** - классическая слоистая архитектура для аналитики и отчетности.

2. Основные слои DWH:

```md
RAW → ODS → DDS → Datamart → Report
```

3. Greenplum может использоваться как единая платформа для хранения и обработки, но при росте нагрузки возникают проблемы конкуренции ресурсов.

4. Для разделения нагрузки можно использовать связку:

```md
Greenplum + Spark + ClickHouse + Trino + Airflow
```

5. Основная боль классического DWH - задержка данных от источника до отчета.

6. **Lambda Architecture** добавляет streaming-контур, чтобы получать быстрые, почти актуальные данные.

7. В Lambda Architecture:

```md
Streaming Layer - быстро, но не всегда точно
Batch Layer - медленно, но точнее
```

8. CDC и Kafka позволяют сделать единую входную точку для batch и streaming.

9. Data Lake решает другую проблему: он позволяет быстро складывать любые данные в дешевое масштабируемое хранилище.

10. Data Lake удобен для ML, ad hoc-аналитики и работы с сырыми данными.

11. Главный риск Data Lake - хаос в данных, сложность поиска, качество и безопасность.

12. Data Lake не является полной заменой DWH. Это другая архитектура со своими плюсами и минусами.
