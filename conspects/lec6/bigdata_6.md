# Лекция 6. Современные архитектуры хранилищ данных: Hybrid DWH/Data Lake, Lakehouse, StreamHouse, Data Mesh и Data Services

## 1. Контекст предыдущих лекций

На предыдущих лекциях рассматривались основные архитектуры хранения и обработки больших данных:

* **DWH / Data Warehouse** — классическое корпоративное хранилище данных.
* **Data Lake** — хранилище сырых и разнородных данных.
* **Lambda Architecture** — архитектура с разделением на:

  * batch layer;
  * speed / streaming layer;
  * serving layer.
* Разные варианты построения DWH, позволяющие ускорять обработку данных.
* Проблемы Data Lake и DWH, которые привели к появлению гибридных архитектур.

Главная идея развития архитектур: компании постепенно двигаются от жестких DWH и файловых Data Lake к более гибким решениям, где можно отдельно масштабировать хранение и вычисления, а также лучше управлять данными.

---

## 2. Гибрид Data Lake и DWH

## 2.1. Зачем появился гибрид

**Data Lake** был призван решить недостатки DWH: дать возможность складывать в единое место большие объемы сырых данных из разных источников.

Но Data Lake принес и свои проблемы:

* риск превращения хранилища в файловую помойку;
* слабая управляемость данных;
* сложность для бизнес-пользователей;
* недостаток структурированных слоев для аналитики.

Поэтому следующей итерацией стала гибридная архитектура, которая объединяет:

* преимущества **Data Lake** — дешевое хранение больших объемов сырых данных;
* преимущества **DWH** — структурированные слои, детализированные данные, витрины и отчетность.

Гибрид Data Lake и DWH — это не просто две системы рядом, а комплексная архитектура, где Data Lake используется как слой хранения сырых данных, а DWH-подход применяется для построения детализированных и аналитических слоев.

---

## 2.2. Организация слоев в гибриде

В гибридной архитектуре сохраняются привычные слои:

```md
Sources
  ↓
Raw / Data Lake layer
  ↓
DDS / detailed layer
  ↓
Data Mart
  ↓
Report layer / BI
```

### Raw layer

**Raw layer** — это слой сырых данных, фактически storage layer для Data Lake.

В него загружаются данные из всех источников через ETL/ELT-пайплайны.

Главная особенность:

> В raw-слой загружаются все данные, даже если они прямо сейчас не нужны бизнесу.

Это позволяет сохранить потенциально полезные данные на будущее.

### DDS layer

**DDS / Detailed Data Store** — детализированный слой данных.

В отличие от raw-слоя, DDS строится только поверх тех объектов, которые сейчас нужны бизнесу.

Примеры сущностей DDS:

* клиент;
* продавец;
* товар;
* заказ;
* счет;
* продукт;
* операция.

DDS можно представить как набор «LEGO-кубиков», из которых затем собираются бизнес-витрины.

### Data Mart

**Data Mart** — слой витрин данных.

Он строится на основе DDS и содержит агрегированные или предметно-ориентированные данные.

Примеры витрин:

* выручка;
* количество проданных товаров;
* рейтинг продавцов;
* активность клиентов;
* показатели по департаментам;
* финансовые метрики.

### Report layer

**Report layer** — слой отчетности, куда обращаются BI-инструменты.

Примеры BI-инструментов:

* Superset;
* Metabase;
* Redash;
* Power BI;
* Tableau.

На этом слое данные обычно представлены в виде широких таблиц, кубов или готовых агрегатов, удобных для менеджмента.

Потребители report layer:

* L1-менеджеры;
* C-level;
* бизнес-аналитики;
* руководители направлений.

---

## 2.3. Доступы и безопасность в гибридной архитектуре

Raw-слой обычно недоступен обычным пользователям.

Причины:

* там лежат сырые, неочищенные данные;
* могут находиться персональные данные;
* данные еще не прошли нормализацию и контроль качества;
* структура данных может быть неудобной для анализа.

Доступ в raw могут иметь:

* технические учетные записи;
* ML-пайплайны;
* разработчики DDS-слоя;
* пользователи, проверяющие технические гипотезы.

Основная бизнес-работа ведется на уровнях:

* DDS;
* Data Mart;
* Report layer.

Именно там размечаются:

* ПДн / персональные данные;
* критичные данные;
* некритичные данные;
* уровни доступа;
* политики информационной безопасности.

---

## 2.4. Compute layer в гибриде

В гибриде, как и в DWH, выделяется отдельный **Compute Layer**.

Он отвечает за:

* регламентные расчеты;
* перекладку данных между слоями;
* batch-обработку;
* streaming-обработку;
* аналитические запросы;
* построение витрин;
* загрузку данных в BI.

Возможные технологии:

* Apache Spark;
* Apache Flink;
* Greenplum;
* ClickHouse;
* StarRocks;
* Trino;
* Airflow или другие оркестраторы.

Compute layer может быть разделен на несколько контуров:

* контур регламентных расчетов;
* контур аналитических запросов;
* test/dev-контур;
* prod-контур.

Однако полноценное разделение dev/test/prod в больших хранилищах дорого, потому что требует синхронизации конфигураций и большого количества инфраструктурных ресурсов.

---

## 2.5. Технологии хранения в гибриде

Для raw-слоя обычно выбирают дешевые и масштабируемые решения:

* HDFS;
* Hadoop ecosystem;
* S3-compatible object storage;
* Apache Ozone;
* YTsaurus;
* Iceberg поверх файлового или объектного хранилища.

Для DDS, Data Mart и Report layer важнее скорость обработки, поэтому могут использоваться:

* Greenplum;
* ClickHouse;
* StarRocks;
* Trino;
* Spark;
* Flink.

Важная мысль лекции:

> Для raw-слоя важнее дешевое и масштабируемое хранение, а для DDS/Data Mart/Report — скорость обработки и качество запросов.

---

## 2.6. Недостатки гибрида Data Lake и DWH

Гибрид решает часть проблем, но остается сложной и дорогой архитектурой.

Основные недостатки:

1. **Долгая поставка данных между слоями**

   Данные проходят путь:

   ```md
   Source → Raw → DDS → Data Mart → Report
   ```

   Каждый переход требует времени, вычислений и сопровождения.

2. **Высокая стоимость владения**

   Нужно поддерживать и Data Lake, и DWH-подход.

3. **Большой технологический зоопарк**

   В архитектуре может быть много разных систем:

   * файловые хранилища;
   * MPP-базы;
   * Spark;
   * Flink;
   * BI;
   * оркестраторы;
   * системы качества данных;
   * системы каталогизации.

4. **Сложность синхронизации команд**

   В некоторых компаниях Data Lake и DWH — разные информационные системы с разными командами, планами и backlog’ами.

5. **Высокие требования к компетенциям**

   Нужны специалисты, которые умеют:

   * проектировать модели данных;
   * оптимизировать запросы;
   * сопровождать инфраструктуру;
   * управлять качеством данных;
   * обеспечивать безопасность.

# 3. Data Lakehouse

## 3.1. Почему появился Data Lakehouse

Мир постепенно стремится решить недостатки гибрида Data Lake и DWH.

Основная цель:

> Сделать хранилище максимально гибким и дешевым, а вычисления отделить от хранения.

Ключевая идея **Data Lakehouse**:

```md
Storage отдельно
Compute отдельно
Metadata отдельно
```

Это позволяет независимо масштабировать:

* место под хранение;
* CPU/RAM под вычисления;
* разные compute-движки под разные нагрузки.

---

## 3.2. Главный принцип: разделение Compute и Storage

В классическом DWH вычисления и хранение часто связаны между собой.

В Lakehouse они разделяются:

```md
Object Storage / File Storage
        +
Table Format
        +
Metadata Catalog
        +
Compute Engines
```

Это позволяет:

* дешево хранить большие объемы данных;
* запускать разные вычислительные движки поверх одного хранилища;
* масштабировать compute независимо от storage;
* уменьшать технологический зоопарк;
* не копировать одни и те же данные между разными системами.

---

## 3.3. Как устроен Data Lakehouse

Концептуально Lakehouse похож на гибрид DWH и Data Lake, но с важным отличием: данные организуются в табличном виде прямо поверх дешевого файлового или объектного хранилища.

Примерная схема:

```md
Sources
  ↓
Object Storage / S3 / HDFS / Ozone
  ↓
Table Format: Iceberg / Hudi / Paimon
  ↓
Metadata Catalog
  ↓
Compute: Spark / Flink / Trino / StarRocks
  ↓
Data Marts / BI / Reports
```

---

## 3.4. Роль metadata storage

В Lakehouse появляется важный компонент — **metadata storage**.

Он хранит информацию о том:

* какие таблицы существуют;
* где лежат файлы таблиц;
* какие у таблиц схемы;
* какие есть партиции;
* какие версии данных существуют;
* какие snapshot’ы доступны;
* как читать данные как таблицу.

Когда аналитический инструмент отправляет SQL-запрос, compute engine сначала обращается к метаданным, чтобы понять, какие файлы читать и как интерпретировать их как таблицу.

---

## 3.5. Табличные форматы

Lakehouse строится поверх табличных форматов.

Основные варианты:

| Формат             | Где полезен                                               |
| ------------------ | --------------------------------------------------------- |
| **Apache Iceberg** | Batch-обработка, большие таблицы, snapshot’ы, аналитика   |
| **Apache Hudi**    | Upsert-сценарии, insert/update, инкрементальные изменения |
| **Apache Paimon**  | Streaming-сценарии, хорошая интеграция с Flink            |
| **Delta Lake**     | Lakehouse-подход, особенно в Databricks ecosystem         |

В лекции основной акцент был на **Apache Iceberg**.

---

## 3.6. Iceberg в Lakehouse

Iceberg позволяет обращаться к данным в S3/HDFS/Ozone как к таблицам.

Фактически данные остаются файлами, но Iceberg добавляет:

* табличную структуру;
* схему;
* snapshot’ы;
* версионирование;
* партиционирование;
* metadata layer;
* оптимизацию чтения.

Пример:

```sql
SELECT *
FROM iceberg.sales.orders
WHERE order_date >= '2026-01-01';
```

Пользователь пишет SQL как к обычной таблице, а Iceberg и compute engine разбирают, какие файлы нужно прочитать.

---

## 3.7. Ограничения Iceberg

Iceberg хорошо подходит для batch-сценариев, но хуже подходит для интенсивной потоковой обработки.

Проблема:

* потоковая обработка порождает много маленьких файлов;
* создается много версий;
* объектное хранилище вроде S3 не любит огромное количество мелких файлов;
* чтение и обслуживание metadata может стать дорогим;
* производительность может деградировать.

Поэтому для streaming-сценариев часто лучше подходит **Apache Paimon** или другие форматы, ориентированные на потоковую обработку.

---

## 3.8. Report layer в Lakehouse

Иногда Lakehouse не дает достаточной скорости для отчетности напрямую из S3 + Iceberg.

Тогда report layer может выноситься в более быстрые системы:

* ClickHouse;
* StarRocks;
* Druid;
* Pinot;
* Greenplum.

Например:

```md
S3 + Iceberg
  ↓
Materialized View / Aggregation
  ↓
ClickHouse
  ↓
BI
```

Так можно ускорить тяжелые отчеты и дашборды.

---

## 3.9. Преимущества Data Lakehouse

Основные преимущества:

1. **Разделение хранения и вычислений**

   Можно отдельно масштабировать storage и compute.

2. **Снижение стоимости на горизонте 3–5 лет**

   В моменте миграция может быть дорогой, но в долгосрочной перспективе архитектура дает экономию.

3. **Единообразное хранение**

   Данные лежат в одном месте, а не размазаны по множеству систем.

4. **Меньше технологического зоопарка**

   Не нужно поддерживать большое количество отдельных хранилищ под разные слои.

5. **Гибкость**

   Поверх одного storage можно запускать разные compute engines:

   * Spark;
   * Flink;
   * Trino;
   * StarRocks;
   * ClickHouse.

---

## 3.10. Недостатки Data Lakehouse

Недостатки:

* не всегда хорошо подходит для real-time;
* streaming-сценарии требуют особой настройки;
* Iceberg может плохо работать с огромным количеством мелких файлов;
* нужна зрелая metadata-инфраструктура;
* требуются компетенции в table formats;
* BI-запросы напрямую к object storage могут быть медленными;
* в некоторых случаях все равно нужен быстрый report layer.

---

# 4. StreamHouse

## 4.1. Почему появился StreamHouse

Data Lakehouse хорошо подходит для batch-аналитики, но не всегда подходит для real-time и потоковой обработки.

Многим компаниям нужны данные, которые актуальны только «здесь и сейчас».

Такие данные можно назвать **скоропортящимися**.

Примеры:

* текущий статус клиента;
* события в call-центре;
* мошеннические операции;
* онлайн-транзакции;
* действия пользователей на сайте;
* логирование запросов;
* состояние очередей;
* мониторинг инфраструктуры;
* актуальный портфель клиента.

Если такие данные обработать через сутки, они могут уже не иметь бизнес-ценности.

---

## 4.2. Главная идея StreamHouse

**StreamHouse** — архитектура хранилища, ориентированная на потоковую обработку данных.

Главный принцип:

> Данные не загружаются по расписанию, а поступают непрерывным потоком.

Обычно данные собираются с помощью:

* CDC / Change Data Capture;
* брокеров сообщений;
* streaming connectors;
* лог-агентов;
* событийных шин.

Пример потока:

```md
Source DB / Logs / Events
  ↓
CDC / Log Collector
  ↓
Kafka / Pulsar
  ↓
Flink Streaming Processing
  ↓
ODS → DWD → DWS → ADS
```

---

## 4.3. Слои StreamHouse

В лекции были выделены четыре основных слоя:

```md
ODS → DWD → DWS → ADS
```

### ODS — Operational Data Store

**ODS** — операционный слой данных.

В StreamHouse часто нет смысла хранить совсем сырые raw-данные, потому что потоковые данные быстро теряют ценность.

Поэтому данные сразу проходят первичную очистку и попадают в ODS.

На ODS-слое выполняются:

* прием событий;
* первичная очистка;
* нормализация;
* объединение данных из разных источников;
* формирование единого ключа;
* дедупликация;
* техническая валидация.

Пример:

Один клиент может существовать в нескольких системах:

* банковской;
* брокерской;
* страховой.

В ODS нужно понять, что это один и тот же клиент, хотя в разных системах у него разные идентификаторы.

---

### DWD — Data Warehouse Detail

**DWD / Data Warehouse Detail** — слой детальных данных.

На этом уровне формируются детальные бизнес-сущности.

Примеры:

* клиент-физлицо;
* клиент-юрлицо;
* продукт;
* счет;
* обращение;
* операция;
* сделка;
* контакт с оператором.

DWD — это слой «кубиков», из которых потом собираются агрегаты и прикладные продукты.

---

### DWS — Data Warehouse Summary

**DWS / Data Warehouse Summary** — слой агрегатов и преданалитики.

Здесь данные уже имеют аналитический смысл.

Примеры:

* текущий брокерский портфель клиента;
* список продуктов клиента;
* количество активных продуктов;
* последний контакт с оператором;
* последний финансовый советник;
* текущее состояние обращения;
* предагрегированные показатели поведения клиента.

---

### ADS — Application Data Service / Analytics Data Service

**ADS** — слой готовых данных для потребителей.

Эти данные могут использоваться:

* BI-инструментами;
* операторами call-центра;
* внешними системами;
* ML-сервисами;
* внутренними приложениями.

ADS предоставляет данные в форме, удобной для конечного использования.

---

## 4.4. Пример StreamHouse: call-центр

Пример из лекции:

Клиент звонит в call-центр, общается с оператором, но связь обрывается.

Затем клиент звонит повторно и попадает к другому оператору.

Если нет real-time-хранилища, новый оператор будет заново спрашивать:

* кто клиент;
* что произошло;
* какой был вопрос;
* какие действия уже выполнялись.

Это ухудшает клиентский опыт и увеличивает время звонка.

При наличии StreamHouse новый оператор может сразу увидеть:

* с кем клиент говорил;
* какой был контекст;
* что уже было сделано;
* какой следующий шаг;
* можно ли переключить клиента на прежнего оператора.

Здесь данные должны быть актуальны в реальном времени, иначе бизнес-ценность теряется.

---

## 4.5. Compute layer в StreamHouse

В StreamHouse compute layer делится на:

1. **аналитический compute**;
2. **streaming processing compute**.

Streaming processing должен быть выделен отдельно.

Причина:

> Потоковая обработка очень чувствительна к задержкам и дополнительной нагрузке.

Если на streaming compute появляются «шумные соседи», поток может начать отставать.

Последствия:

* растет очередь сообщений;
* увеличивается latency;
* данные устаревают;
* обработка становится бессмысленной;
* инфраструктура продолжает тратить деньги, но бизнес-ценность падает.

Поэтому streaming processing лучше размещать:

* на отдельных физических машинах;
* на отдельных инстансах;
* в отдельном Kubernetes node pool;
* с отдельными лимитами ресурсов;
* без конкуренции с batch-нагрузкой.

---

## 4.6. Технологии StreamHouse

Основная технология, выделенная в лекции, — **Apache Flink**.

Flink хорошо подходит для StreamHouse, потому что:

* изначально ориентирован на потоковую обработку;
* имеет Flink CDC;
* интегрируется с Apache Paimon;
* умеет обрабатывать бесконечные потоки;
* поддерживает event time;
* поддерживает stateful processing;
* подходит для низкой задержки.

Возможный стек:

```md
Flink CDC
  ↓
Kafka / Pulsar
  ↓
Flink
  ↓
Apache Paimon + S3
  ↓
DWD / DWS / ADS
```

Для низколатентных сценариев могут добавляться memory / key-value storage:

* Redis;
* Valkey;
* Dragonfly;
* Aerospike;
* KeyDB.

Также могут использоваться wide-column базы:

* Cassandra;
* ScyllaDB;
* HBase.

Для BI или report layer может использоваться:

* ClickHouse;
* StarRocks;
* S3 + Paimon;
* другие аналитические движки.

---

## 4.7. ClickHouse и streaming

ClickHouse хорошо подходит для быстрой записи и чтения больших объемов данных.

Но важно помнить:

> ClickHouse не является классической OLTP-базой с полноценными update-операциями.

В ClickHouse данные чаще не обновляются «на месте», а перезаписываются через механики insert/delete, merge или специальные движки таблиц.

То есть ClickHouse хорошо подходит для:

* append-only данных;
* логов;
* событий;
* аналитических запросов;
* быстрых агрегаций.

Но с частыми update/delete его нужно использовать аккуратно.

---

## 4.8. Преимущества StreamHouse

Преимущества:

1. **Высокая скорость обработки**

   Данные доступны почти в реальном времени.

2. **Актуальность аналитики**

   Можно видеть состояние клиента, системы или процесса «здесь и сейчас».

3. **Работа с большими потоками событий**

   Подходит для high-load-сценариев.

4. **Поддержка real-time бизнес-процессов**

   Например:

   * call-центр;
   * антифрод;
   * мониторинг;
   * персонализация;
   * онлайн-рекомендации.

---

## 4.9. Недостатки StreamHouse

Недостатки:

1. **Сложность реализации**

   StreamHouse сложнее проектировать, чем batch-хранилище.

2. **Высокая стоимость сопровождения**

   Нужно постоянно следить за latency, очередями, state, checkpoint’ами, отказами.

3. **Хрупкость инфраструктуры**

   Любая деградация может привести к накоплению очередей.

4. **Высокая стоимость ресурсов**

   Real-time обработка дорогая.

5. **Ограниченность исторической аналитики**

   StreamHouse показывает текущее состояние, но не всегда удобен для ретроспективного анализа.

Для полноценной исторической аналитики часто нужен DWH, Lakehouse или холодное хранилище.

---

# 5. Сбор логов в streaming

## 5.1. Как логи попадают в streaming

Обычно приложения пишут логи в файлы.

Чтобы превратить логи в поток, используются специальные агенты и коллекторы, которые следят за изменениями файлов и отправляют новые записи дальше.

Примеры инструментов:

* Logstash;
* Vector;
* Fluentd;
* Filebeat;
* Grafana Agent / Alloy;
* Promtail для Loki.

Схема:

```md
Application logs
  ↓
Log collector
  ↓
Kafka / another broker
  ↓
Stream processing
  ↓
OpenSearch / ClickHouse / Loki / S3
```

---

## 5.2. Пример: аудит запросов Hadoop

В лекции приводился пример с логами Hadoop.

Задача:

* в реальном времени собирать аудит пользовательских запросов;
* понимать, кто какие данные запрашивает;
* определять востребованность данных;
* искать плохие запросы;
* останавливать тяжелые запросы;
* давать рекомендации по оптимизации.

Это важно, потому что один плохой запрос может ухудшить работу множества других хороших запросов.

---

# 6. OpenSearch, ELK и Grafana Loki

## 6.1. OpenSearch

**OpenSearch** часто используется как замена Elasticsearch.

Он подходит для:

* логов;
* полнотекстового поиска;
* неструктурированных данных;
* поиска по Lucene-индексам;
* анализа событий.

OpenSearch особенно хорошо применять там, где нужно искать по тексту:

* сообщения логов;
* ошибки;
* stack trace;
* audit logs;
* события приложений.

Для классической аналитики по структурированным данным OpenSearch обычно не лучший выбор.

---

## 6.2. Apache Doris

В лекции упоминался **Apache Doris** как возможная альтернатива для некоторых сценариев, в том числе аналитики и полнотекстового поиска.

Но акцент был на том, что в российских компаниях OpenSearch встречается чаще, чем Doris в production.

---

## 6.3. ELK

**ELK** — классический стек:

```md
Elasticsearch
Logstash
Kibana
```

Он хорошо подходит для:

* сбора логов;
* хранения логов;
* полнотекстового поиска;
* построения дашбордов;
* анализа ошибок;
* расследования инцидентов.

В лекции отмечалось, что ELK часто дает больше возможностей для анализа логов, чем Grafana Loki.

---

## 6.4. Grafana Loki

**Grafana Loki** — альтернатива для хранения и анализа логов, особенно если в компании уже используется Grafana-экосистема.

Обычно рядом используются:

* Prometheus — для метрик;
* Loki — для логов;
* Tempo — для трассировок;
* Grafana — для визуализации.

Преимущество Loki:

* хорошо интегрируется с Grafana;
* удобен, если Prometheus/Grafana уже внедрены;
* может быть проще в эксплуатации.

Ограничение:

* для глубокого анализа логов ELK/OpenSearch часто гибче.

---

## 6.5. Что выбрать: ELK или Grafana + Loki

Выбор зависит от контекста.

Если в компании уже есть Prometheus и Grafana, логично идти по пути меньшего сопротивления и использовать Loki.

Если нужна мощная система анализа логов и полнотекстового поиска, предпочтительнее ELK/OpenSearch.

Общая рекомендация из лекции:

```md
Метрики → Prometheus + Grafana
Логи → OpenSearch / ELK
Трейсы → Tempo / Jaeger
```

# 7. Data Mesh

## 7.1. Зачем нужен Data Mesh

Когда данных становится очень много, недостаточно просто сложить их в единое хранилище.

Нужно уметь:

* понимать, где какие данные лежат;
* кто за них отвечает;
* какого они качества;
* кому их можно выдавать;
* какие данные критичны;
* какие данные являются продуктом;
* как данные связаны с бизнес-доменами.

С ростом объема данных централизованная команда хранилища перестает справляться со всем самостоятельно.

Так появляется концепция **Data Mesh**.

---

## 7.2. Главная идея Data Mesh

**Data Mesh** — это организационно-архитектурный подход, где данные делятся по бизнес-доменам.

Примеры доменов для экосистемной компании:

* такси;
* каршеринг;
* финтех;
* онлайн-кинотеатр;
* e-commerce;
* поиск;
* рекламные сервисы.

Каждый домен отвечает за свои данные.

---

## 7.3. Инверсия ответственности

В классическом подходе команда хранилища сама забирает данные из источников и складывает их в DWH/Data Lake.

В Data Mesh ответственность инвертируется:

> Источники данных сами отвечают за поставку, качество и актуальность своих данных.

Команда хранилища превращается в платформенную команду.

Она отвечает не за ручную загрузку всех данных, а за:

* платформу;
* инструменты;
* методологию;
* стандарты;
* безопасность;
* интеграцию;
* data governance;
* поддержку команд.

---

## 7.4. Data Product

Ключевое понятие Data Mesh — **data product**.

Данные рассматриваются как продукт.

Data product может быть построен:

* только на данных одного домена;
* на пересечении нескольких доменов.

Примеры:

* продукт только на данных финтеха;
* продукт на данных финтеха и такси;
* продукт на данных финтеха и онлайн-кинотеатра;
* продукт на данных нескольких бизнес-направлений.

Каждый data product должен иметь:

* владельца;
* понятное описание;
* SLA;
* качество;
* схему;
* правила доступа;
* документацию;
* потребителей.

---

## 7.5. Роль команды хранилища в Data Mesh

Команда хранилища:

* предоставляет платформу;
* помогает доменам работать с данными;
* поддерживает инструменты;
* помогает интегрировать данные разных доменов;
* задает стандарты;
* обеспечивает Data Governance.

Но она не должна вручную строить все data products под заказ каждого потребителя.

---

## 7.6. Проблемы Data Mesh на практике

В чистом виде Data Mesh встречается редко.

Причины:

* сложно провести границы между доменами;
* команды могут залезать на территорию друг друга;
* появляются дублирующие data products;
* не всегда понятно, кто владелец данных;
* разные команды имеют разную зрелость;
* трудно унифицировать стандарты;
* много организационных конфликтов.

Поэтому компании часто адаптируют Data Mesh под себя.

---

# 8. Data Services

## 8.1. Зачем нужны Data Services

Просто загрузить данные в хранилище недостаточно.

Если не управлять данными, хранилище превращается в файловую помойку.

Проблемы без Data Services:

* пользователи не знают, где искать данные;
* никто не понимает качество данных;
* нет прозрачного описания таблиц;
* сложно выдавать доступы;
* неясно, где персональные данные;
* нет lineage;
* сложно понять влияние изменений;
* много ручной поддержки.

---

## 8.2. Change и Run

В работе с хранилищем есть два типа задач:

| Тип        | Смысл                                                                |
| ---------- | -------------------------------------------------------------------- |
| **Change** | развитие хранилища, новые витрины, новые продукты, новые возможности |
| **Run**    | сопровождение, поддержка, инциденты, ручные запросы, исправления     |

Идеальная картина:

> 90% усилий команды должны уходить на Change, а не на Run.

Чтобы снизить Run-нагрузку, нужно дать пользователям self-service-инструменты.

---

## 8.3. Задача Data Services

Data Services должны скрывать сложность хранилища от пользователя.

Пользователь не должен знать:

* как устроен raw;
* где DDS;
* какие Spark jobs перекладывают данные;
* как устроены DWH-модели;
* какие есть технические зависимости;
* как работает lineage внутри.

Пользователь должен иметь понятный интерфейс:

* найти данные;
* понять описание;
* проверить качество;
* запросить доступ;
* увидеть владельца;
* понять происхождение данных;
* использовать данные в работе.

---

# 9. Основные Data Services

## 9.1. Data Governance

**Data Governance** — это управление данными на уровне политик, стандартов, процессов и контроля.

Data Governance отвечает за:

* правила работы с данными;
* стандарты именования;
* классификацию данных;
* управление метаданными;
* управление доступами;
* аудит;
* безопасность;
* соответствие нормативным требованиям;
* жизненный цикл данных;
* обучение сотрудников;
* контроль качества процессов.

Без Data Governance хранилище быстро становится хаотичным.

Пример:

Команда не должна выкатывать новую витрину без проверки:

* корректности naming conventions;
* описания атрибутов;
* классификации данных;
* наличия владельца;
* правил доступа;
* соответствия требованиям безопасности.

---

## 9.2. Data Quality

**Data Quality** — непрерывный процесс контроля качества данных.

Его задача — обнаруживать проблемы как можно раньше.

Это соответствует принципу **Shift Left**:

> Ошибки нужно находить на ранних этапах обработки, а не тогда, когда пользователь уже увидел плохой отчет.

Data Quality включает:

* проверки полноты;
* проверки уникальности;
* проверки форматов;
* проверки допустимых значений;
* проверки свежести данных;
* проверки ссылочной целостности;
* очистку данных;
* стандартизацию;
* мониторинг;
* алертинг;
* блокировку некорректных данных.

Пример:

Если котировки акций сегодня выглядят аномально по сравнению со вчерашним днем, система качества должна обнаружить это до того, как данные попадут в отчет.

---

## 9.3. Data Catalog

**Data Catalog** — путеводитель пользователя по данным.

Это единая входная точка для поиска данных в хранилище.

Пользователь должен иметь возможность:

* открыть каталог;
* ввести запрос;
* найти нужную таблицу или витрину;
* прочитать описание;
* посмотреть владельца;
* увидеть схему;
* посмотреть sample данных;
* понять связи с другими таблицами;
* запросить доступ.

Пример запроса:

```md
"данные клиентов банка"
```

На выходе пользователь должен получить список таблиц и витрин, где есть такие данные.

---

## 9.4. Data Catalog и безопасность

Data Catalog должен показывать:

* есть ли в таблице персональные данные;
* какие поля чувствительные;
* какой уровень критичности;
* кто владелец данных;
* кто может согласовать доступ;
* какие политики применяются.

Если у пользователя нет доступа к ПДн, он должен либо:

* запросить доступ;
* найти обезличенную альтернативу;
* использовать агрегированные данные.

---

## 9.5. Data Lineage

**Data Lineage** — это описание пути данных от источника до конечной витрины.

Он показывает:

```md
Source systems
  ↓
ODS / Raw
  ↓
DDS / DWD
  ↓
Data Mart / DWS
  ↓
Report / ADS
```

Data Lineage отвечает на вопросы:

* откуда пришли данные;
* какие трансформации применялись;
* какие таблицы зависят от этой таблицы;
* какие отчеты сломаются при изменении поля;
* где возникла ошибка;
* кто владелец источника;
* как данные попали в витрину.

---

## 9.6. Зачем нужен Data Lineage

Data Lineage полезен для:

1. **Поиска источника проблемы**

   Если в отчете неправильное значение, lineage помогает найти, на каком этапе оно испортилось.

2. **Impact analysis**

   Если меняется DDL таблицы, можно понять, какие downstream-таблицы, витрины и отчеты будут затронуты.

3. **Предотвращения дублирования**

   Можно увидеть, что нужные данные уже где-то считаются.

4. **Аудита**

   Можно объяснить происхождение данных регулятору, безопасности или бизнесу.

5. **Управления изменениями**

   Команды видят зависимости и могут безопаснее менять пайплайны.

---

## 9.7. Почему Data Lineage выделяется в отдельный сервис

В хранилищах слои обычно не связаны foreign key.

Например:

* Spark читает таблицу A и пишет таблицу B;
* Greenplum-скрипт читает DDS и пишет Data Mart;
* Airflow запускает DAG, который перекладывает данные;
* Flink пишет потоковые агрегаты.

Связи между таблицами существуют не в самой базе, а в коде, SQL, DAG’ах и runtime-логах.

Data Lineage должен собирать метаинформацию из разных мест:

* Spark jobs;
* SQL-запросы;
* Greenplum;
* Airflow;
* Flink;
* BI;
* metadata catalog;
* orchestration logs.

---

## 9.8. Инструменты для Data Lineage и Catalog

В лекции упоминались:

* Apache Atlas;
* Marquez;
* OpenLineage;
* DataHub;
* Amundsen.

На практике часто встречаются:

* DataHub;
* OpenLineage;
* Apache Atlas.

# 10. Шпаргалка по архитектурам

| Архитектура                | Когда использовать                             | Преимущества                                      | Недостатки                                          |
| -------------------------- | ---------------------------------------------- | ------------------------------------------------- | --------------------------------------------------- |
| **DWH**                    | Структурированная корпоративная отчетность     | Управляемость, качество, понятные слои            | Дорого, долго, менее гибко                          |
| **Data Lake**              | Хранение больших объемов сырых данных          | Дешевое хранение, гибкость                        | Риск файловой помойки, сложность управления         |
| **Hybrid DWH + Data Lake** | Когда нужны и сырые данные, и DWH-слои         | Объединяет плюсы Lake и DWH                       | Дорого, сложно, много технологий                    |
| **Data Lakehouse**         | Единое хранилище с разделением compute/storage | Гибкость, масштабируемость, экономия на горизонте | Сложность metadata, ограничения real-time           |
| **StreamHouse**            | Real-time и потоковая обработка                | Актуальные данные, низкая задержка                | Очень дорого и сложно, ограниченная историчность    |
| **Data Mesh**              | Большая организация с множеством доменов       | Ответственность доменов, данные как продукт       | Сложно организационно, редко работает в чистом виде |

# 11. Как проектировать хранилище данных

При проектировании хранилища нужно начинать не с технологий, а с целей.

## 11.1. Сначала определить цели

Нужно ответить на вопросы:

* зачем нужны данные;
* кто потребители;
* какие бизнес-процессы зависят от данных;
* нужна ли историческая аналитика;
* нужен ли real-time;
* какие отчеты нужны;
* нужны ли ML-сценарии;
* какие SLA по свежести данных;
* какие требования по безопасности.

---

## 11.2. Собрать профиль нагрузки

Важно понять:

* больше чтения или записи;
* batch или streaming;
* равномерная нагрузка или пики;
* какие объемы данных;
* какой latency допустим;
* сколько пользователей;
* какие запросы будут выполняться;
* нужны ли частые update/delete;
* нужно ли хранить историю.

Профиль нагрузки влияет на выбор архитектуры и технологий.

---

## 11.3. Выбрать базовую архитектуру

После сбора требований выбирается основа:

* DWH;
* Data Lake;
* Hybrid DWH + Data Lake;
* Data Lakehouse;
* StreamHouse;
* гибридная архитектура.

Далее архитектура дорабатывается под специфику компании.

---

## 11.4. Не откладывать Data Services

Важный вывод лекции:

> Data Services нужно закладывать в архитектуру сразу.

Если сначала построить хранилище без Data Governance, Data Catalog, Data Quality и Data Lineage, оно может превратиться в файловую помойку.

Потом внедрять управление будет намного сложнее.

---

## 11.5. Хранилище — это не проект, а процесс

Работа с хранилищем данных не имеет конечной точки.

Это не проект с началом и концом, а постоянный процесс:

* появляются новые источники;
* меняются требования бизнеса;
* растут объемы данных;
* появляются новые витрины;
* меняются регуляторные требования;
* появляются новые потребители;
* нужно оптимизировать стоимость;
* нужно поддерживать качество.

Поэтому команда хранилища всегда будет заниматься и Change, и Run.

# 12. Ключевые выводы лекции

1. **Гибрид Data Lake и DWH** объединяет дешевое хранение сырых данных и структурированные аналитические слои.

2. **Raw-слой** обычно недоступен бизнес-пользователям; основная работа идет через DDS, Data Mart и Report layer.

3. **Data Lakehouse** стремится разделить compute и storage, чтобы снизить стоимость и повысить гибкость.

4. **Iceberg** хорошо подходит для batch Lakehouse, но не идеален для интенсивного streaming.

5. **StreamHouse** нужен там, где данные имеют ценность только в реальном времени.

6. **Flink** — один из ключевых инструментов для построения потоковой архитектуры.

7. **Streaming processing** нужно изолировать от других нагрузок, потому что задержки быстро приводят к устареванию данных.

8. **OpenSearch/ELK** хорошо подходят для логов и полнотекстового поиска.

9. **Grafana + Loki** — хорошая альтернатива, если компания уже использует Grafana/Prometheus ecosystem.

10. **Data Mesh** переносит ответственность за данные ближе к доменным командам и источникам.

11. **Data Product** — данные, оформленные как продукт с владельцем, качеством, SLA и документацией.

12. **Data Services** нужны, чтобы пользователи могли самостоятельно находить, понимать и использовать данные.

13. **Data Governance, Data Quality, Data Catalog и Data Lineage** — обязательные элементы зрелого хранилища.

14. **При проектировании хранилища нужно начинать с целей, требований и профиля нагрузки, а не с выбора технологий.**
