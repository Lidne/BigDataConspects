# Конспект лекции: Compute Layer, ETL/ELT, инструменты обработки данных и архитектура DWH

## 1. Контекст лекции

На предыдущих занятиях рассматривались **stack-технологии Big Data**: хранение данных, модели данных, форматы хранения, разделение технологий на решения типа **Compute + Storage** и отдельно выделяемые **Storage Layer** и **Compute Layer**.

В этой лекции основной фокус смещается на **Compute Layer** — слой вычислений, то есть технологии, которые позволяют:

* извлекать данные из источников;
* трансформировать данные;
* перекладывать данные между хранилищами;
* строить витрины и отчёты;
* выполнять batch- и streaming-обработку;
* обслуживать аналитические запросы.

Ключевая идея: **хранилища данных менять дорого, а вычислительный слой менять намного проще**.

Если компания уже загрузила десятки или сотни петабайт данных в хранилище, миграция в другое хранилище становится очень дорогой задачей. Часто нужно держать одновременно старое и новое хранилище, синхронизировать их и постепенно переводить потребителей. Это резко увеличивает **TCO — Total Cost of Ownership**, то есть совокупную стоимость владения.

Compute Layer более гибкий, потому что вычислительные приложения обычно можно контейнеризировать или виртуализировать. В Big Data и High Load редко запускают приложения прямо на **bare metal** без изоляции, потому что такие приложения сложнее обслуживать, чистить, переносить и восстанавливать после сбоев.

## 2. ETL и ELT

Перед изучением конкретных инструментов важно понимать два базовых подхода к обработке данных:

* **ETL — Extract, Transform, Load**
* **ELT — Extract, Load, Transform**

В транскрипции термин ETL был искажён как «Extract of Formation Logging», но корректная расшифровка — **Extract, Transform, Load**.

---

## 3. ETL: Extract, Transform, Load

**ETL** — это подход, при котором данные сначала извлекаются из источника, затем трансформируются в промежуточном вычислительном слое и только после этого загружаются в целевую систему.

Схема:

```text
Source → Extract → Transform → Load → Target / Sink
```

Где:

* **Source** — источник данных: СУБД, API, брокер сообщений, файловая система и т.д.
* **Transform** — преобразование данных: очистка, нормализация, агрегация, обогащение.
* **Load** — загрузка в целевую систему.
* **Sink** — система-получатель данных.

ETL часто используется в классических **DWH / Data Warehouse**-архитектурах, где пользователь не должен видеть данные до того, как они прошли проверку и трансформацию.

Преимущество ETL: на выходе пользователь получает уже подготовленные, очищенные и структурированные данные.

Недостаток ETL: данные становятся доступны только после завершения трансформации.

---

## 4. ELT: Extract, Load, Transform

**ELT** — это подход, при котором данные сначала извлекаются из источника, затем в сыром виде загружаются в целевое хранилище, а уже потом трансформируются внутри этого хранилища.

Схема:

```text
Source → Extract → Load → Raw Storage → Transform
```

ELT чаще связан с архитектурами типа:

* **Data Lake**
* **Data Lakehouse**
* хранилища с большим raw-слоем;
* сценарии, где важно быстро сохранить данные в исходном виде.

Главная идея ELT: сначала сохранить данные «как есть», а уже потом решать, какие трансформации нужны для аналитики.

Преимущество ELT: данные быстро попадают в хранилище, и пользователи или инженеры могут работать с raw-данными.

Недостаток ELT: сырые данные могут быть невалидными, неполными, несогласованными и неудобными для бизнес-аналитики.

---

## 5. Способы извлечения данных из источников

На этапе **Extract** есть несколько основных подходов.

---

## 6. Snapshot-загрузка

**Snapshot** — это полная выгрузка текущего состояния источника.

Пример: есть таблица в PostgreSQL или MySQL. Вместо того чтобы искать только новые или изменённые записи, мы каждый день полностью копируем таблицу в хранилище.

Схема:

```text
Source DB → полный снимок таблицы → Target Storage
```

Преимущества snapshot:

* самый простой подход;
* почти не требует сложной логики;
* легко реализовать;
* подходит для небольших таблиц;
* хорош для быстрого Time to Market.

Недостатки snapshot:

* занимает много дискового пространства;
* неэффективен для больших таблиц;
* каждый раз перегружает весь объём данных;
* плохо подходит для таблиц на десятки или сотни терабайт.

Snapshot оправдан, если источник небольшой, например таблица на 100 МБ, и нет смысла усложнять архитектуру инкрементальной логикой.

---

## 7. Инкрементальная загрузка

**Инкрементальная загрузка** — это выгрузка только тех данных, которые появились или изменились после предыдущей загрузки.

Для этого нужно хранить некоторый маркер последней выгрузки:

* дату последней загрузки;
* максимальный `id`;
* timestamp изменения;
* служебную таблицу с метаданными загрузки.

Схема:

```text
Source DB → только новые / изменённые записи → Target Storage
```

Преимущества инкрементальной загрузки:

* экономит дисковое пространство;
* снижает объём передаваемых данных;
* подходит для больших таблиц;
* гибче, чем snapshot.

Недостатки:

* требует дополнительной логики;
* нужно хранить метаданные загрузок;
* нужно корректно определять инкремент;
* возможны ошибки при изменениях схемы или при некорректных идентификаторах.

Инкрементальная загрузка особенно полезна, когда не хочется ежедневно перегружать огромные таблицы, например на 100 ТБ.

---

## 8. CDC — Change Data Capture

**CDC — Change Data Capture** — это подход, при котором изменения захватываются на стороне источника, обычно через журнал транзакций.

В транскрипции термин **Write-Ahead Log** был искажён как «write a headlock» и «wall file». Корректно:

* **WAL — Write-Ahead Log**;
* **transaction log** — журнал транзакций;
* для MySQL часто используется **binlog**;
* также встречаются redo logs.

Когда в СУБД происходит операция:

* `INSERT`;
* `UPDATE`;
* `DELETE`;

она записывается в журнал транзакций. CDC-приложение читает этот журнал и публикует события изменений дальше, например в брокер сообщений.

Типичная структура CDC-события:

```text
before: состояние записи до изменения
after: состояние записи после изменения
```

Преимущества CDC:

* не нужно тяжёлыми запросами нагружать основную СУБД;
* изменения доставляются почти в реальном времени;
* хорошо подходит для streaming-архитектур;
* можно публиковать изменения в Kafka или другой брокер сообщений.

Недостатки CDC:

* CDC-приложение должно стабильно читать журнал;
* если CDC «залипнет», WAL/binlog может начать разрастаться;
* журнал может удерживаться и не архивироваться;
* при проблемах CDC может начать влиять на источник.

CDC часто используется как начало потока обработки данных.

---

## 9. Pull-модель и Push-модель

При обычной инкрементальной загрузке часто используется **pull-модель**:

```text
ETL по расписанию сам приходит в источник и забирает данные
```

Например, раз в час ETL-задача проверяет, появились ли новые записи.

В CDC ближе **push-модель**:

```text
изменения почти сразу отправляются в поток / брокер сообщений
```

CDC-приложение постоянно следит за журналом изменений и при появлении нового события публикует его дальше.

## 10. Apache Spark

**Apache Spark** — один из основных инструментов распределённой и параллельной обработки больших данных.

Spark построен на концепции **MapReduce**, но не является классической технологией Hadoop MapReduce.

Основная идея:

1. данные распределены по множеству машин;
2. задача отправляется в Spark;
3. Spark разбивает задачу на части;
4. вычисления выполняются параллельно на разных узлах;
5. промежуточные результаты перемешиваются через shuffle;
6. результат собирается и возвращается пользователю.

Spark скрывает от пользователя сложность распределённых вычислений. Пользователь может писать код так, будто работает с одной машиной, но Spark сам параллелит выполнение по кластеру.

---

## 11. MapReduce-концепция в Spark

Концепция MapReduce состоит из нескольких этапов:

```text
Map → Shuffle → Reduce
```

* **Map** — данные читаются и обрабатываются по частям.
* **Shuffle** — данные перераспределяются по ключам между узлами.
* **Reduce** — данные с одинаковыми ключами агрегируются или финально обрабатываются.

Пример:

```sql
SELECT user_id, COUNT(*)
FROM sessions
GROUP BY user_id;
```

Spark:

1. найдёт, где лежат данные;
2. отправит вычисления ближе к данным;
3. выполнит локальные агрегации;
4. выполнит shuffle по `user_id`;
5. соберёт итоговый результат.

---

## 12. Языки и интерфейсы Spark

Spark написан преимущественно на:

* Java;
* Scala.

При этом он предоставляет интерфейсы для:

* Python — **PySpark**;
* SQL — **Spark SQL**;
* Java;
* Scala.

PySpark важен, потому что снижает порог входа для аналитиков и дата-инженеров, которые чаще работают с Python, а не с Java или Scala.

---

## 13. Batch и Streaming в Spark

Изначально Spark был ориентирован прежде всего на **batch-обработку**:

```text
загрузили большую пачку данных → обработали → записали результат
```

Позже появилась возможность streaming-обработки через микробатчи.

**Micro-batch** — это подход, при котором потоковые данные обрабатываются маленькими пакетами с небольшой задержкой.

То есть Spark может работать не только по расписанию, но и почти в режиме реального времени, например обрабатывая события из Kafka.

---

## 14. Apache Flink

**Apache Flink** — конкурент Spark, но с другим историческим фокусом.

Если Spark изначально развивался как инструмент для batch-обработки, то Flink изначально создавался с акцентом на **streaming processing**.

Главная цель Flink — минимизация **latency**, то есть задержки между появлением события и его обработкой.

Flink особенно полезен там, где данные должны обрабатываться постоянно:

* координаты пользователя на карте;
* clickstream;
* события с устройств;
* телеком-события;
* блокировки SIM-карт;
* изменение баланса;
* антифрод;
* мониторинг.

---

## 15. Spark vs Flink

| Критерий            | Apache Spark                               | Apache Flink                                        |
| ------------------- | ------------------------------------------ | --------------------------------------------------- |
| Исторический фокус  | Batch                                      | Streaming                                           |
| Потоковая обработка | Через micro-batch / Structured Streaming   | Native streaming                                    |
| Основная область    | Регламентные расчёты, большие batch-задачи | Низкая задержка, обработка 24/7                     |
| Языки               | Scala, Java, Python, SQL                   | Java, Scala, Python, SQL                            |
| Python-интерфейс    | PySpark                                    | PyFlink                                             |
| Типовые задачи      | ETL, витрины, пересчёты, batch-аналитика   | Потоки событий, near real-time, streaming analytics |

Важно: и Spark, и Flink развиваются в сторону универсальности. Spark умеет streaming, а Flink может использоваться и для batch-задач.

---

## 16. Trino

**Trino** — SQL-движок для распределённых ad hoc-запросов к разным источникам данных.

Ключевая идея Trino: пользователь пишет SQL, а Trino может обращаться к разным хранилищам.

Пример условного запроса:

```sql
SELECT *
FROM postgres.table_a
JOIN clickhouse.table_b ON ...
JOIN hadoop.table_c ON ...;
```

Trino может подключаться к разным источникам и выполнять SQL-запрос поверх них.

---

## 17. Когда использовать Trino

Trino хорошо подходит для **ad hoc analytics** — разовых аналитических запросов.

Пример: аналитик хочет срочно посмотреть сегмент клиентов с портфелем больше 100 млн рублей и подготовить рассылку. Такой запрос нужен здесь и сейчас, но не обязательно должен ежедневно пересчитываться.

Trino не лучший выбор для регулярных тяжёлых пайплайнов, которые должны стабильно работать по расписанию. Для этого лучше подходят Spark или Flink.

---

## 18. Spark/Flink vs Trino

| Критерий             | Spark / Flink                         | Trino                                          |
| -------------------- | ------------------------------------- | ---------------------------------------------- |
| Основной сценарий    | ETL, ELT, batch, streaming            | Ad hoc SQL-запросы                             |
| Подход               | Код отправляется к данным             | Данные подтягиваются для обработки SQL-движком |
| Пользователи         | Data Engineers, продвинутые аналитики | Аналитики, BI, data analysts                   |
| Регулярные витрины   | Да                                    | Лучше не использовать как основной инструмент  |
| Разовые исследования | Можно, но тяжелее                     | Очень удобно                                   |

---

## 19. StarRocks

**StarRocks** — аналитическая СУБД/движок, который, как и Trino, умеет работать с внешними источниками данных.

Важное понятие — **Shared Data architecture**.

StarRocks может:

* хранить данные внутри себя;
* подключаться к external storage;
* создавать external tables;
* выполнять аналитические запросы;
* использовать оптимизации на уровне современных процессоров, включая SIMD.

Отличие от Trino:

* Trino сам по себе не является полноценным хранилищем;
* StarRocks может быть и вычислительным движком, и хранилищем.

---

## 20. Apache NiFi

**Apache NiFi** — инструмент для построения потоков обработки данных в low-code/no-code стиле.

NiFi предоставляет веб-интерфейс, где можно собирать workflow из процессоров:

```text
Processor → Queue → Processor → Queue → Processor
```

Пользователь добавляет процессоры, настраивает их, соединяет очередями и запускает поток.

Примеры процессоров:

* чтение из FTP/SFTP;
* чтение из HDFS;
* обработка JSON;
* обработка CSV;
* публикация в Kafka;
* запись в СУБД;
* CDC-процессоры, например CaptureChangeMySQL.

NiFi удобен для быстрых интеграционных задач, особенно когда не хочется писать полноценный код.

---

## 21. Роль NiFi в Big Data

NiFi не всегда подходит для очень больших объёмов данных, но полезен для:

* прототипирования;
* студенческих проектов;
* интеграции источников;
* автоматизации небольших потоков;
* построения простых ingestion pipeline;
* no-code обработки файлов и событий.

Код в NiFi нужен только тогда, когда стандартных процессоров недостаточно и нужно написать собственный processor или расширить существующий.

---

## 22. Визуализация данных и BI

После обработки и хранения данных возникает задача: **принять решение на основе данных**.

Сырые таблицы сложно читать, особенно топ-менеджерам и бизнес-пользователям. Поэтому используются BI-инструменты — **Business Intelligence**.

BI-инструменты позволяют строить:

* графики;
* диаграммы;
* таблицы;
* дашборды;
* отчёты;
* интерактивные фильтры;
* регулярные обновляемые витрины.

BI обычно смотрит на уже подготовленные данные: Data Mart или Report Layer.

---

## 23. BI-инструменты

В лекции были упомянуты:

* **Apache Superset**
* **Metabase**
* **Redash**
* **DataLens**
* **Excel**

### Apache Superset

Open-source BI-инструмент с широкими возможностями визуализации и интеграции с разными источниками данных.

Подходит для компаний, которые хотят кастомизировать BI под свои источники и инфраструктуру.

### Metabase

Более простой и лёгкий инструмент. Хорош для небольших проектов, где не требуется сложная кастомизация.

### Redash

Тоже простой, но достаточно мощный инструмент для SQL-аналитики и дашбордов.

### DataLens

BI-инструмент, который может работать как облачно, так и on-premise. Может использоваться не только для визуализации данных, но и как более интерактивный интерфейс для пользователей.

### Excel

В лекции подчёркивается, что Excel остаётся одним из самых распространённых инструментов работы с данными. Даже если данные подготовлены в DWH и визуализированы в BI, бизнес-пользователи часто всё равно выгружают их в Excel.

## 24. Архитектуры хранилищ данных

Дальше лекция переходит к архитектурам хранения данных. Это особенно важно для System Design и Data Intensive Systems.

Базовые архитектуры:

1. **Data Warehouse / DWH / EDW**
2. **Data Lake**
3. **Data Lakehouse**
4. **Streaming-oriented Lakehouse**
5. **AI House** как новая концепция

---

## 25. Data Warehouse

**Data Warehouse / DWH** — это корпоративное хранилище данных со слоистой архитектурой.

Также встречаются термины:

* **EDW — Enterprise Data Warehouse**
* **КХД — корпоративное хранилище данных**
* **ЕКХД — единое корпоративное хранилище данных**

Главная идея DWH: данные проходят через несколько слоёв, и каждый слой имеет своё назначение, качество данных и круг пользователей.

Классическая цепочка:

```text
Sources → RAW → ODS → DDS → Data Mart → Report
```

---

## 26. Data Lake

**Data Lake** — это архитектура, где данные хранятся в более плоской структуре, часто в сыром, полуструктурированном или неструктурированном виде.

Data Lake должен был решить часть проблем DWH, но принёс свои сложности.

Преимущества Data Lake:

* можно хранить любые данные;
* удобно сохранять raw-данные;
* хорошо подходит для больших объёмов;
* гибче в отношении схемы данных.

Недостатки:

* сложнее обеспечить качество данных;
* можно получить «болото данных» — data swamp;
* аналитикам труднее работать без структурированных витрин;
* нужна дисциплина каталогизации, метаданных и governance.

---

## 27. Data Lakehouse

**Data Lakehouse** — гибрид Data Lake и Data Warehouse.

Он пытается объединить:

* гибкость Data Lake;
* структурированность и управляемость DWH;
* поддержку транзакционности;
* поддержку аналитики;
* меньший TCO в долгосрочной перспективе.

Lakehouse сложнее реализовывать и поддерживать, но стратегически он может быть более гибким и дешёвым.

---

## 28. Streaming-oriented архитектура

Следующий этап развития — архитектура, где в основу Lakehouse добавляется **streaming processing**.

Идея:

```text
все данные должны обрабатываться в real-time или near real-time
```

Такая архитектура дороже, но полезна для данных с коротким сроком жизни:

* антифрод;
* телеком-события;
* кликовые события;
* мониторинг;
* финансовые транзакции;
* события IoT;
* актуальная персонализация.

---

## 29. AI House

В лекции также упомянута новая концепция — **AI House**.

Идея: значительную часть работы с данными выполняет не человек, а AI-система.

Возможный сценарий:

```text
Пользователь спрашивает: "Где посмотреть данные по клиентам?"
AI анализирует метаданные хранилища
AI предлагает таблицу, описание данных и SQL-запрос
```

Другой сценарий:

```text
Пользователь просит: "Сделай ежедневный отчёт"
AI генерирует DAG / pipeline / SQL / описание витрины
```

Технически такая система может использовать:

* каталог метаданных;
* RAG-подход;
* SQL generation;
* lineage;
* data contracts;
* документацию по таблицам;
* историю запросов;
* BI-слой.

# 30. Слои Data Warehouse

## 30.1 RAW Layer

**RAW Layer** — слой сырых данных.

В него данные загружаются из источников почти без трансформаций.

Примеры источников:

* MySQL;
* PostgreSQL;
* Kafka;
* API;
* сетевые папки;
* FTP/SFTP;
* файлы;
* внешние системы.

Данные в RAW могут быть:

* структурированными;
* полуструктурированными;
* неструктурированными;
* JSON;
* XML;
* бинарными файлами;
* изображениями;
* аудио;
* видео.

RAW-слой нужен для того, чтобы сохранить данные в исходном виде.

---

## 30.2 Зачем нужен RAW Layer

RAW Layer даёт несколько преимуществ.

### 1. Историчность

Источник может не хранить исторические данные. Например, система хранит только данные текущего дня, а потом очищает их.

DWH забирает эти данные в RAW и хранит историю уже у себя.

### 2. Защита от изменений источника

Если в источнике изменилась схема, например добавились или удалились колонки, RAW-слой позволяет отследить, когда именно это произошло.

Такие изменения относятся к **DDL — Data Definition Language**.

### 3. Data Contracts

Для загрузки в RAW важно заключать **data contract**.

В data contract фиксируется:

* откуда забираются данные;
* как часто забираются данные;
* каким способом: snapshot, increment, CDC, push, pull;
* какая схема ожидается;
* как источник должен предупреждать об изменениях;
* за сколько времени до релиза источник обязан уведомить потребителей.

Нарушение data contract может привести к тому, что данные перестанут загружаться.

### 4. Снижение нагрузки на источник

Если не иметь RAW-слоя, аналитики и downstream-системы будут постоянно обращаться к источнику.

Но источник может быть слабым, например маленький MySQL с ограниченным CPU и памятью. Поэтому DWH один раз забирает данные в RAW, а дальше все внутренние расчёты идут уже от RAW-слоя.

### 5. Технический доступ

RAW-слой обычно предназначен не для людей, а для технических учётных записей и ETL/ELT-процессов.

Человек не должен вручную ходить в RAW, потому что:

* данные сырые;
* данные могут быть невалидными;
* формат может быть машиночитаемым;
* легко нарушить целостность;
* для аналитики этот слой неудобен.

---

## 30.3 ODS Layer

**ODS — Operational Data Store**.

ODS — это слой операционных данных, где данные из разных источников уже объединяются и приводятся к более удобному виду.

Пример: есть три источника данных о клиенте:

* биллинговая система;
* CRM;
* система авторизации.

Каждая система содержит часть данных о клиенте. В ODS формируется единая сущность «Клиент».

На ODS-слое решаются задачи:

* объединение данных из разных источников;
* дедупликация;
* приоритизация источников;
* выбор более доверенного источника для конкретного атрибута;
* первичная валидация;
* подготовка к операционной аналитике.

ODS уже более читаемый, чем RAW, но ещё не является финальным бизнес-слоем.

---

## 30.4 DDS Layer

**DDS — Detailed Data Store**.

DDS — слой детализированных данных.

На этом слое данные нормализуются и раскладываются на отдельные сущности.

Здесь могут использоваться модели:

* 3NF;
* Data Vault;
* Star Schema;
* Snowflake Schema;
* факты и измерения.

DDS хранит детальные сущности, из которых потом собираются витрины.

Также на этом уровне может храниться история изменений, например через:

* **SCD — Slowly Changing Dimensions**.

DDS нужен не столько бизнесу напрямую, сколько дата-инженерам, аналитикам и системам, которые строят дальнейшие витрины.

---

## 30.5 Data Mart Layer

**Data Mart** — слой витрин данных.

Витрина данных строится под конкретный бизнес-домен или бизнес-задачу.

Примеры витрин:

* финансовая витрина;
* витрина доходов;
* витрина расходов;
* маркетинговая витрина;
* клиентская витрина;
* витрина поведения пользователей;
* витрина продаж;
* витрина рисков.

Главное отличие Data Mart от DDS:

* в DDS лежат детальные технические сущности;
* в Data Mart лежат данные, удобные для бизнес-аналитики.

Пример из лекции:

В DDS могут лежать отдельные данные по акциям и облигациям клиента. А в Data Mart уже должны быть бизнес-атрибуты:

* доход по акциям;
* доход по облигациям;
* общий доход;
* агрегированные показатели портфеля.

---

## 30.6 Report Layer

**Report Layer** — слой готовых отчётов.

Это опциональный слой, но он часто используется для ускорения BI.

Идея:

```sql
SELECT *
FROM report.some_ready_table;
```

То есть BI-инструменту не нужно выполнять сложные join-запросы к витринам. Он просто читает готовую широкую таблицу.

Report Layer нужен для:

* ускорения дашбордов;
* снижения нагрузки на Data Mart;
* упрощения BI-запросов;
* предоставления данных топ-менеджерам;
* регулярной отчётности.

---

# 31. Поток данных в DWH

Классический ночной расчёт может выглядеть так:

```text
00:00 — загрузка из источников в RAW
01:00 — обработка RAW → ODS
02:00 — обработка ODS → DDS
03:00 — обработка DDS → Data Mart
04:00 — построение Report Layer
06:00–09:00 — бизнес получает готовые отчёты
```

DWH часто имеет SLA: данные должны быть готовы к определённому времени, например к 7, 9 или 10 утра.

Если один слой не успел рассчитаться, downstream-слои тоже не запустятся. Поэтому DWH требует надёжной оркестрации и мониторинга.

---

## 32. Оркестрация

Для запуска ETL/ELT-задач по расписанию используется orchestration layer.

Пример инструмента:

* **Apache Airflow**

Airflow запускает DAG — граф задач.

Пример зависимости:

```text
RAW job finished → ODS job starts
ODS job finished → DDS job starts
DDS job finished → Data Mart job starts
Data Mart job finished → Report job starts
```

Если задача сломалась посередине, финальные отчёты могут не появиться вовремя.

---

## 33. Технологическая архитектура DWH

Архитектура DWH включает несколько уровней.

```text
Sources
   ↓
Storage Layer: RAW → ODS → DDS → Data Mart → Report
   ↑
Compute Layer: Spark / Flink / SQL jobs / Trino / StarRocks
   ↑
Orchestration Layer: Airflow / scheduler
   ↓
Analytics & BI: Superset / Metabase / Redash / DataLens / Excel
```

Важно разделять compute-ресурсы:

1. для регламентных ETL/ELT-процессов;
2. для аналитиков и ad hoc-запросов;
3. для BI-дашбордов.

Если аналитики будут использовать те же ресурсы, что и ночные ETL-задачи, они могут нарушить расписание загрузок.

| Слой      | Кто работает                                          | Назначение                       |
| --------- | ----------------------------------------------------- | -------------------------------- |
| RAW       | Data Engineers, технические процессы                  | Сырые данные из источников       |

| Data Mart | BI, Data Analysts, Business Analysts, Data Scientists | Бизнес-витрины                   |

## 35. Medallion Architecture

В лекции также упоминалась медальонная архитектура, где слои называются по ценности данных для бизнеса.

| Medallion слой | Примерное соответствие DWH | Смысл                                            |
| -------------- | -------------------------- | ------------------------------------------------ |
| Bronze         | RAW / частично ODS         | Сырые или почти сырые данные                     |
| Silver         | ODS / DDS                  | Очищенные, объединённые, детализированные данные |
| Gold           | Data Mart                  | Бизнес-витрины                                   |
| Platinum       | Report                     | Готовые отчёты для потребителей                  |

Чем выше слой, тем больше бизнес-ценность данных и тем проще с ними работать конечному пользователю.

| Слой      | Возможные модели                                    |
| --------- | --------------------------------------------------- |
| RAW       | Как в источнике, файлы, JSON, XML, бинарные форматы |
| ODS       | Объединённые сущности, частичная нормализация       |
| DDS       | 3NF, Data Vault, Star Schema, Snowflake Schema      |

## 37. Что происходит, если для отчёта не хватает данных

Если бизнес просит новый отчёт, а в Report Layer нужных данных нет, запрос идёт вниз по слоям.

```text
Report не хватает данных
→ проверяем Data Mart
→ если не хватает, проверяем DDS
→ если не хватает, проверяем ODS
→ если не хватает, проверяем RAW
→ если не хватает, подключаем новый источник
```

Самая сложная ситуация — когда нужных данных нет даже в RAW. Тогда нужно:

* найти новый источник;
* заключить data contract;
* настроить ingestion;
* добавить данные в RAW;
* перестроить ODS;
* обновить DDS;
* построить новую витрину;
* обновить отчёт.

Поэтому на ранних этапах создания DWH задачи могут быть долгими и дорогими: ещё не все источники подключены, не все сущности описаны, не все витрины готовы.

## 38. Inmon и Kimball

В лекции упоминались классические подходы к построению DWH:

* **Bill Inmon** — подход к корпоративному хранилищу данных сверху вниз;
* **Ralph Kimball** — подход через витрины и размерное моделирование.

Разные компании могут по-разному называть слои:

```text
Staging → Core → Presentation
```

Или:

```text
RAW → ODS → DDS → Data Mart → Report
```

Или через Medallion:

```text
Bronze → Silver → Gold → Platinum
```

Названия различаются, но логика похожа: от сырья к всё более подготовленным и бизнес-ценным данным.

# 40. Главные выводы лекции

1. **Compute Layer более гибкий, чем Storage Layer.** Хранилище мигрировать дорого, а вычислительные инструменты проще заменить или развернуть в контейнерах.

2. **ETL и ELT — разные подходы.** В ETL данные сначала трансформируются, потом загружаются. В ELT данные сначала сохраняются в сыром виде, а потом трансформируются.

3. **Extract можно делать через snapshot, increment или CDC.** Snapshot проще, increment экономит объём, CDC позволяет строить поток изменений почти в реальном времени.

4. **Spark — стандарт для batch-обработки больших данных.** Он скрывает сложность распределённых вычислений, но для оптимального кода нужно понимать MapReduce, shuffle и устройство кластера.

5. **Flink сильнее ориентирован на streaming.** Он лучше подходит для задач, где важна минимальная задержка и постоянная обработка событий.

6. **Trino удобен для ad hoc-аналитики.** Это SQL-движок, который позволяет обращаться к разным источникам данных в одном запросе.

7. **NiFi полезен для no-code/low-code ingestion pipeline.** Он удобен для быстрых интеграций, обработки файлов, CDC и автоматизации потоков.

8. **BI-инструменты нужны для принятия решений.** Бизнесу редко нужны сырые таблицы; ему нужны отчёты, дашборды и понятные визуализации.

9. **DWH строится слоями.** Основные слои: RAW, ODS, DDS, Data Mart, Report.

10. **Чем выше слой DWH, тем больше бизнес-ценность данных.** RAW нужен инженерам, Report — бизнесу и C-level.

11. **Надёжность DWH зависит от оркестрации.** Если один слой не рассчитался вовремя, бизнес может не получить отчёты к нужному времени.

12. **Подключение нового источника — одна из самых трудоёмких задач.** Оно требует изменений во всех слоях: от RAW до Report.
