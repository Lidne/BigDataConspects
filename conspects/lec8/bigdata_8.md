# Конспект лекции 8. System/Data System Design: streaming processing, форматы данных и DWH-архитектура

## 1. Контекст лекции

Лекция продолжает разбор задач **system design / data system design** для систем анализа больших данных. Основной фокус:

1. Доработка архитектуры для сбора кликов из мобильного приложения в реальном времени.
2. Выбор технологий для streaming processing.
3. Декомпозиция Flink-приложения.
4. Выбор форматов хранения данных.
5. Разбор новой задачи: построение корпоративного DWH для рыночных данных по финансовым инструментам.
6. Обсуждение архитектурных компромиссов: DWH, Data Lake, Lambda Architecture, Streamhouse.
7. Практические рекомендации по прохождению system design-интервью.

---

## 2. Задача 1: сбор кликов из мобильного приложения

### 2.1. Постановка задачи

Рассматривается задача system design, похожая на задачу с интервью в банке, вероятно, в **Т-Банке / Тинькофф**. Есть мобильное приложение, из которого нужно:

* собирать клики пользователей;
* делать это в режиме реального времени;
* предоставлять клики или агрегаты потенциальным системам-потребителям;
* поддерживать аналитику;
* спроектировать архитектуру, технологии, хранение, интерфейсы доступа и поставку данных.

---

## 3. Варианты архитектуры для кликов

### 3.1. Вариант 1: один общий streaming processing-модуль

Первый вариант — построить один общий модуль потоковой обработки:

```text
Мобильное приложение
        ↓
Kafka / очередь событий
        ↓
Streaming Processing
        ↓
Хранилище логов / агрегатов
        ↓
Потребители / аналитика
```

Плюс такого подхода — простота архитектуры.

Минусы:

* streaming processing становится слишком крупным и монолитным;
* сложнее независимо масштабировать разные части обработки;
* сложнее менять отдельные этапы;
* повышается риск при релизах;
* при изменении одной части приходится тестировать весь пайплайн.

---

### 3.2. Вариант 2: разделение исторической загрузки и агрегатора

Второй вариант — концептуально разделить систему на две части:

```text
Мобильное приложение
        ↓
Kafka
        ↓
1. Ingestion / загрузка истории
        ↓
Общее хранилище логов

Kafka
        ↓
2. Streaming Aggregator
        ↓
Готовые агрегаты
        ↓
Потребители
```

Идея:

* первая часть отвечает за загрузку исходных событий в историческое хранилище;
* вторая часть отвечает за построение конкретных агрегатов;
* исторические данные можно забирать из основного хранилища;
* быстрые агрегаты можно хранить отдельно.

Такой подход более гибкий, потому что историческое хранение и оперативная обработка не смешиваются в один компонент.

---

## 4. Разделение хранилища по температуре данных

В лекции предлагается делить хранилище на несколько уровней.

### 4.1. Холодные данные

Это исторические данные, которые редко читаются.

Возможные технологии:

* S3;
* Apache Iceberg;
* Apache Paimon;
* HDFS;
* архивное файловое хранилище.

Назначение:

* хранение истории;
* переобработка;
* аудит;
* долгосрочный анализ;
* восстановление агрегатов.

---

### 4.2. Горячие агрегаты

Это данные, которые часто запрашиваются аналитическими системами или API.

Возможные технологии:

* ClickHouse;
* StarRocks;
* Greenplum, если речь о классическом DWH;
* специализированные OLAP-хранилища.

Назначение:

* быстрые аналитические запросы;
* BI;
* API для потребителей;
* витрины данных.

---

### 4.3. Сверхгорячий слой / временные окна

Это данные, которые нужны для коротких временных окон и оперативного состояния.

Возможные технологии:

* Redis;
* Aerospike;
* in-memory state внутри Flink;
* внешнее key-value-хранилище.

Назначение:

* дедупликация;
* хранение временных окон;
* быстрый state lookup;
* кэширование промежуточных состояний.

---

## 5. Как рассуждать на system design-интервью

Важная мысль лекции: в system design обычно **нет единственного правильного решения**.

Цель кандидата — показать:

* широту кругозора;
* понимание trade-off’ов;
* способность связывать архитектурные решения с требованиями;
* умение объяснять плюсы и минусы;
* способность защищать решение;
* готовность менять архитектуру при появлении новых ограничений.

Интервьюер может специально «челленджить» решение:

* задавать вопросы про минусы;
* спрашивать, где система сломается;
* просить снизить latency;
* просить уменьшить стоимость;
* просить упростить поддержку;
* просить объяснить, почему выбран именно этот стек.

Важно не просто назвать технологию, а объяснить, **почему она подходит именно под требования задачи**.

---

## 6. Выбор технологий для streaming processing

### 6.1. ETL и ELT

В зависимости от архитектуры можно использовать разные подходы:

#### ETL

```text
Extract → Transform → Load
```

Сначала данные извлекаются, затем обрабатываются, затем загружаются в хранилище.

Подходит, когда:

* нужно сразу привести данные к нужному формату;
* есть строгие требования к качеству;
* нельзя загружать «сырые» данные в основное хранилище.

#### ELT

```text
Extract → Load → Transform
```

Сначала данные загружаются в хранилище, затем трансформируются внутри него.

Подходит, когда:

* хранилище достаточно мощное;
* нужно сохранить raw-историю;
* трансформации удобно делать SQL’ем;
* данные сначала складываются, потом агрегируются.

---

## 7. Сравнение технологий потоковой обработки

### 7.1. Apache Flink

**Apache Flink** — основной кандидат для потоковой обработки.

Преимущества:

* низкая latency;
* настоящая потоковая обработка;
* развитая экосистема source/sink-коннекторов;
* поддержка stateful processing;
* хорошо подходит для окон, дедупликации, enrichment;
* гибко интегрируется с разными хранилищами;
* хорошо сочетается с Kafka, S3, Paimon, Iceberg.

Flink особенно уместен, если нужна минимальная задержка и гибкая обработка потока.

---

### 7.2. Apache Spark

Spark тоже может использоваться для потоковой обработки, особенно через **Spark Structured Streaming** и режимы, снижающие latency.

Но важный аргумент против Spark в этой задаче:

* Spark исторически больше ориентирован на **micro-batch**;
* Flink лучше подходит для настоящего streaming;
* если latency должна быть минимальной, Flink обычно предпочтительнее.

Spark можно выбрать, если:

* задержка в минуты допустима;
* команда уже хорошо знает Spark;
* большая часть обработки batch-oriented;
* нет строгих требований к real-time.

---

### 7.3. Trino

**Trino** в данной задаче не является основным кандидатом.

Причина:

* Trino — это в первую очередь SQL-движок для аналитики по уже существующему конечному набору данных;
* он не предназначен быть основным streaming processing-движком;
* он хорош для запросов, но не для обработки непрерывного потока событий.

---

### 7.4. StarRocks

**StarRocks** может использоваться для online analytics и потоковой загрузки.

Возможности:

* Continuous Load;
* интеграция с Apache Flink;
* StarRocks Pipe;
* быстрые аналитические запросы.

Но есть архитектурный минус: если использовать StarRocks как часть streaming processing, возникает сильная связность между обработкой и конкретным хранилищем.

Проблема:

```text
Обработка завязана на StarRocks
        ↓
Хотим заменить хранилище
        ↓
Приходится менять не только storage, но и processing-часть
```

Для хорошей архитектуры лучше, чтобы компоненты были слабосвязаны.

---

### 7.5. Apache NiFi

**Apache NiFi** — low-code/no-code-инструмент для построения data flow.

Плюсы:

* легко настраивать;
* можно соединять процессоры стрелочками;
* удобно для простых интеграций;
* быстро поднимать пайплайны без большого объёма разработки.

Минусы:

* плохо подходит для очень больших объёмов данных;
* хуже масштабируется;
* может стать узким местом;
* не лучший выбор для high-load streaming processing.

В лекции делается вывод: для больших потоков остаются два основных кандидата — **Flink** и **StarRocks**, но при ориентации на S3 + Paimon / Iceberg предпочтительнее **Flink**.

---

## 8. Принцип слабой связности компонентов

Одна из ключевых архитектурных идей лекции: компоненты системы должны быть **гибкими и слабосвязанными**.

Плохой вариант:

```text
Источник → кастомная обработка → кастомное хранилище → кастомный API
```

Минус: при замене одного компонента приходится переписывать много соседних частей.

Хороший вариант:

```text
Источник
   ↓
Kafka
   ↓
Flink
   ↓
универсальное хранилище
   ↓
стандартные интерфейсы доступа
```

Kafka здесь выступает как универсальный интеграционный интерфейс.

Если нужно заменить streaming processing:

```text
Flink → другая технология
```

часть до Kafka может остаться прежней.

Если нужно заменить хранилище:

```text
ClickHouse → StarRocks / Druid / Greenplum
```

processing можно менять меньше, если sink-интерфейс стандартный.

---

## 9. Почему не стоит выбирать слишком кастомные технологии

В лекции подчёркивается: узкоспециализированные или самописные решения несут риск.

Их можно брать, если они дают **кардинальный выигрыш**.

Например:

* Redis оправдан, если нужен быстрый in-memory доступ;
* Kafka оправдана как универсальная шина событий;
* Flink оправдан для сложного streaming processing.

Но если замена ClickHouse на StarRocks не даёт явного выигрыша, а просто кажется «модной», это не является хорошим архитектурным аргументом.

## 10. Декомпозиция Flink-приложения

### 10.1. Почему нельзя всё делать одной Flink-job

Наивное решение:

```text
Одна большая Flink-job:
read → validate → clean → enrich → deduplicate → aggregate → write
```

Проблема в том, что разные этапы имеют разный профиль нагрузки.

---

### 10.2. Разные профили нагрузки

#### Фильтрация и валидация

Обычно нагружают CPU.

Причины:

* проверка правил;
* преобразование типов;
* фильтрация мусорных событий;
* простые вычисления;
* мало состояния в памяти.

Пример ресурсов:

```text
4 CPU / 1 GB RAM
```

---

#### Дедупликация, enrichment, агрегирование

Обычно требуют больше памяти.

Причины:

* нужно хранить state;
* нужно помнить уже обработанные события;
* нужно держать временные окна;
* может понадобиться lookup во внешнее хранилище.

Пример ресурсов:

```text
1 CPU / 4 GB RAM
```

---

### 10.3. Логика разделения Flink-приложения

Хороший вариант — разделить приложение на несколько крупных этапов:

```text
Source
  ↓
Flink Job 1: read → validate → clean → normalize
  ↓
Kafka / internal pipe / gRPC
  ↓
Flink Job 2: repartition → enrich → compute → aggregate
  ↓
Storage / Kafka increment / API
```

Но не нужно разбивать каждый маленький шаг на отдельный сервис.

Плохой вариант:

```text
read → Kafka → validate → Kafka → clean → Kafka → normalize → Kafka → enrich
```

Такой подход создаёт слишком большой overhead:

* сериализация;
* десериализация;
* запись в Kafka;
* чтение из Kafka;
* сетевые задержки;
* рост нагрузки на инфраструктуру.

---

## 11. Баланс между монолитом и микросервисами

### 11.1. Монолитный streaming processing

Плюсы:

* минимальная latency;
* меньше сетевых переходов;
* меньше сериализации/десериализации;
* проще трассировать один процесс.

Минусы:

* большой релизный цикл;
* изменение одной части требует тестирования всего приложения;
* выше риск регрессии;
* сложнее независимо масштабировать этапы;
* сложнее менять логику.

---

### 11.2. Полностью микросервисная обработка

Плюсы:

* каждый сервис отвечает за одну функцию;
* можно независимо релизить;
* можно независимо масштабировать;
* проще локально тестировать отдельные блоки.

Минусы:

* большой overhead на сеть;
* больше Kafka topics / REST / gRPC-вызовов;
* сложнее эксплуатация;
* сложнее мониторинг;
* выше latency.

---

### 11.3. Практический компромисс

Оптимальное решение — не чистый монолит и не «микросервис на каждую операцию», а декомпозиция по крупным блокам с разным профилем нагрузки.

Например:

```text
Job 1: ingestion + validation + normalization
Job 2: repartition + stateful processing + aggregation
Job 3: writing + publishing increments
```

---

## 12. Масштабирование через Kafka partitions

### 12.1. Ограничение параллелизма

Максимальный параллелизм чтения из Kafka ограничен количеством partitions в topic.

Если в topic 10 partitions, то эффективно можно иметь максимум 10 активных consumer’ов в одной consumer group.

```text
Topic: 10 partitions
        ↓
Consumer group: максимум 10 активных читателей
```

Если запустить 11-й consumer, он не получит partition и не будет читать данные.

---

### 12.2. Что делать, если partitions в source Kafka мало

Иногда source Kafka не принадлежит нам, и мы не можем изменить количество partitions.

Например:

```text
Source Kafka: 10 partitions
```

Но нам нужно 20 потоков обработки.

Решение:

```text
Source Kafka: 10 partitions
        ↓
легкая Flink-job / Kafka Streams / ingestion job
        ↓
собственная Kafka: 20 partitions
        ↓
основная обработка в 20 потоков
```

При перекладывании данных в свою Kafka важно делать минимум бизнес-логики:

* прочитать;
* назначить корректный key;
* перераспределить;
* записать в topic с большим числом partitions.

---

## 13. Факторы декомпозиции streaming processing

При проектировании нужно учитывать:

* CPU-нагрузку;
* RAM-нагрузку;
* disk I/O;
* network I/O;
* latency;
* требования к надёжности;
* сложность релизов;
* стоимость эксплуатации;
* пропускную способность сети.

Если сеть 10 Gbit/s, избыточная декомпозиция может стать проблемой.

Если сеть 100 Gbit/s, большее число сервисов и обменов может быть допустимым.

## 14. Форматы данных для первой задачи

### 14.1. Почему не CSV / TSV / JSON / XML

Текстовые форматы плохо подходят для больших аналитических объёмов.

Минусы:

* долго парсятся;
* занимают больше места;
* требуют полного чтения структуры;
* хуже подходят для ML и аналитики;
* нет эффективного column pruning;
* нет нормальной метаинформации для быстрого чтения;
* плохо работают с bloom filters и predicate pushdown.

---

### 14.2. Почему нужен колоночный формат

В задаче есть агрегаты по действиям пользователя. Например:

```text
client_id
action_1_count
action_2_count
...
action_153_count
```

Если действий 153, то удобно хранить каждое действие отдельной колонкой.

Преимущество:

* можно читать только нужные колонки;
* не нужно вытаскивать всю строку целиком;
* аналитические запросы работают быстрее;
* проще добавлять новые действия как новые колонки;
* эффективнее сжатие.

---

### 14.3. Parquet vs ORC vs Avro

#### Avro

Avro — строковый формат.

Он хорош для:

* streaming;
* Kafka;
* передачи событий;
* schema evolution;
* row-based processing.

Но для аналитического хранения агрегатов он хуже, потому что не является колоночным.

---

#### ORC

ORC — колоночный формат, хорошо работает в Hadoop/Hive-экосистеме.

Минус в контексте лекции:

* больше ориентирован на Hive;
* менее универсален, чем Parquet.

---

#### Parquet

Parquet — предпочтительный вариант для аналитического хранения.

Плюсы:

* колоночный формат;
* бинарный;
* поддерживает сжатие;
* поддерживает строгую схему;
* широко поддерживается аналитическими движками;
* хорошо работает с Apache Iceberg;
* универсальнее ORC.

Вывод по первой задаче: для аналитического хранения агрегатов лучше выбрать **Parquet**.

---

## 15. Задача 2: единое хранилище рыночных данных

### 15.1. Постановка задачи

Рассматривается более классическая DWH-задача.

Есть корпоративный сервис сбора и обработки рыночных данных о финансовых инструментах:

* акции;
* облигации;
* фонды;
* другие финансовые инструменты.

Источники данных стабильны и заранее известны:

* Московская биржа;
* Cbonds;
* Bloomberg;
* ЦБ РФ;
* НРД — Национальный расчётный депозитарий;
* другие внешние поставщики.

Нужно собирать данные, объединять их по финансовым инструментам и формировать единую цену по утверждённой методике.

---

### 15.2. Что такое единая цена

Разные источники могут давать разные цены по одному инструменту.

Например, по одной акции могут быть данные:

```text
Московская биржа → цена A
Bloomberg        → цена B
Cbonds           → цена C
ЦБ РФ            → цена D
```

Система должна применить утверждённый алгоритм и получить единую цену.

```text
Набор цен из источников
        ↓
Методика выбора цены
        ↓
Единая цена
        ↓
Витрина данных
```

---

## 16. Основные функции DWH для рыночных данных

Система должна обеспечивать:

1. Интеграцию с источниками рыночных данных.
2. Хранение исторических данных.
3. Реализацию методики выбора цены.
4. Разработку витрин данных.
5. Формирование информационных потоков по требованиям заказчиков.
6. Доступ аналитиков и руководства к унифицированным данным.

---

## 17. Три ключевые задачи сервиса

### 17.1. Единый справочник инструментов

Нужно иметь единый справочник финансовых инструментов.

Он должен позволять найти инструмент независимо от того, как он обозначается в разных источниках.

Например:

```text
Источник A: instrument_id_1
Источник B: ticker_2
Источник C: ISIN
Источник D: internal_code
        ↓
Единый инструмент в DWH
```

---

### 17.2. Консолидация данных

Данные из разных источников должны быть приведены к единой модели.

Цель:

* сопоставимость;
* контроль качества;
* единый формат;
* единые правила обработки;
* единая история.

---

### 17.3. Удобный доступ

Потребители должны получать данные через:

* SQL;
* BI-инструменты;
* API;
* витрины;
* отчётность.

## 19. Почему это похоже на классический DWH

Задача очень близка к классическому корпоративному DWH, потому что:

* источники стабильны;
* данные нужно нормализовать;
* требуется единая модель;
* важна историчность;
* нужны витрины;
* основная обработка batch T-1;
* пользователи знают SQL;
* требования к качеству и управляемости выше, чем к raw-гибкости.

Базовая схема:

```text
Источники
   ↓
RAW / STG
   ↓
ODS
   ↓
DDS
   ↓
Data Marts
   ↓
BI / API / отчётность
```

## 20. Data Lake в этой задаче

Data Lake можно использовать, но не как основной центр архитектуры.

Проблема Data Lake:

* он больше про хранение разнородных данных;
* хуже соответствует требованию единого формата;
* требует отдельно продумывать безопасность;
* не всегда удобен для SQL-only аналитиков;
* может усложнить governance.

Но Data Lake полезен для:

* архивного хранения;
* ледяного слоя;
* хранения старой истории;
* бэкапов;
* редких тяжёлых отчётов;
* долгосрочной ретенции.

---

## 21. Lambda Architecture, Streamhouse или DWH

### 21.1. Lambda Architecture

Lambda Architecture может подойти, если есть и batch, и streaming.

```text
Источники
   ↓
Kafka
   ├── Batch layer → DWH
   └── Speed layer → Flink → ClickHouse / API
```

Плюс:

* можно закрыть batch T-1;
* можно поддержать частичный real-time.

Минус:

* архитектура становится сложнее;
* нужно поддерживать две ветки обработки;
* возможна дубликация логики.

---

### 21.2. Streamhouse

Streamhouse мог бы быть интересным вариантом, но в этой задаче он, скорее всего, избыточен.

Минусы:

* сложнее обеспечить историчность;
* выше стоимость поддержки;
* сильная ориентация на streaming и CDC;
* не вся логика удобно выражается SQL’ем;
* для SQL-only аналитиков сложнее;
* задача требует эффективного варианта, а не максимально модной архитектуры.

---

### 21.3. Классический DWH с частичным streaming

Наиболее разумный вариант из лекции:

```text
Основная обработка: batch DWH
Частичный real-time: Kafka + Flink + ClickHouse/API
Архив: S3 + Iceberg / HDFS / холодное хранилище
```

---

## 22. Почему Airflow, а не CDC

CDC мог бы работать, но в задаче источники стабильны, а данные в основном нужны T-1.

Поэтому CDC может оказаться избыточным:

* дороже поддерживать;
* сложнее сопровождать;
* больше инфраструктуры;
* не всегда нужен real-time.

Вместо этого можно использовать **Airflow**:

```text
Airflow DAG
   ↓
раз в час забирает данные из источников
   ↓
кладёт в Kafka / RAW
```

Преимущества:

* дешевле;
* проще;
* понятнее;
* можно «размазать» нагрузку в течение дня;
* достаточно для T-1.

---

## 23. Kafka как входная точка

Kafka в этой архитектуре используется как:

* буфер;
* балансировщик;
* входная точка для Lambda Architecture;
* почти raw-слой для streaming;
* универсальный интерфейс между источниками и обработкой.

Схема:

```text
Московская биржа
Cbonds
Bloomberg
ЦБ РФ
НРД
API / СУБД / RabbitMQ / файлы
        ↓
Airflow / небольшие ingestion-приложения
        ↓
Kafka
        ↓
DWH batch processing
        ↓
Flink streaming processing
```

## 24. Почему Greenplum подходит как основа DWH

В лекции Greenplum выбирается как основной DWH.

Аргументы:

1. Объём до 100 ТБ хорошо подходит для Greenplum.
2. Нужен классический DWH.
3. Основная обработка batch T-1.
4. Аналитики знают SQL.
5. Нужна MPP-архитектура и горизонтальное масштабирование.
6. Вертикальное масштабирование ограничено.
7. Требуется высокая доступность.
8. Greenplum может быть одновременно хранилищем и вычислительным слоем.
9. Трансформации можно писать SQL’ем.

## 25. Слои данных в Greenplum

Внутри Greenplum данные могут двигаться по классическим слоям.

```text
RAW / STG
   ↓
ODS
   ↓
DDS
   ↓
DataMart
```

### 25.1. RAW / STG

Сырой слой.

Назначение:

* сохранить данные как пришли;
* обеспечить возможность переобработки;
* иметь исторический след загрузки;
* не потерять исходные значения.

---

### 25.2. ODS

Операционный слой.

Назначение:

* первичная очистка;
* нормализация;
* приведение типов;
* разбор JSON/XML/Avro;
* базовая дедупликация;
* подготовка к бизнес-модели.

---

### 25.3. DDS

Детальный слой данных.

Назначение:

* хранение согласованной бизнес-модели;
* историчность;
* связи между сущностями;
* единые справочники;
* качественные данные.

---

### 25.4. DataMart

Витрины.

Назначение:

* отчёты;
* BI;
* API;
* расчёт единой цены;
* подготовленные аналитические наборы.

## 29. Streaming-часть во второй задаче

Так как real-time в задаче нужен только частично, нет необходимости строить огромную streaming-платформу.

Достаточно:

```text
Kafka
  ↓
Flink
  ↓
ClickHouse / API / Redis
```

Flink может выполнять:

* валидацию;
* обогащение;
* расчёт временных окон;
* построение оперативных агрегатов;
* публикацию инкрементов.

Redis можно использовать как вспомогательный кэш.

Cassandra может рассматриваться как промежуточное хранилище для streaming ODS, но, по лекции, возможно, без неё можно обойтись.

Особенности ледяного слоя:

* дешёвое хранение;
* медленный доступ;
* подходит для старых данных;
* подходит для редких тяжёлых отчётов;
* подходит для архивов и бэкапов.

## 31. Форматы данных во второй задаче

### 31.1. Почему не стоит гонять JSON/XML по всему пайплайну

Если источники присылают JSON или XML, не нужно оставлять этот формат на всех слоях.

Минусы JSON/XML:

* занимают больше места;
* дольше парсятся;
* требуют полного разбора документа;
* снижают производительность;
* увеличивают стоимость обработки;
* хуже подходят для streaming и batch на больших объёмах.

---

### 31.2. Почему Avro подходит для Kafka и RAW

Для передачи данных через Kafka и хранения на ранних слоях хорошо подходит **Avro**.

Преимущества Avro:

* бинарный формат;
* строковая организация данных;
* хорошо подходит для потоков;
* хранит схему;
* поддерживает schema evolution;
* есть required и optional поля;
* хорошо работает с Kafka Schema Registry;
* хорошо поддерживается Flink, NiFi, Airbyte и другими ingestion-инструментами.

---

### 31.3. Avro как quality gate

Avro вместе со Schema Registry может выступать как контроль качества.

Если источник начинает отправлять данные по старой или несовместимой схеме, Kafka / Schema Registry может отклонить такие сообщения.

Это важно, потому что ответственность за корректную эволюцию схемы переносится на источник.

```text
Источник отправляет невалидное сообщение
        ↓
Schema Registry отклоняет
        ↓
Источник исправляет схему
        ↓
В DWH не попадает мусор
```

---

### 31.4. Почему Parquet хуже для streaming

Parquet хорош для аналитики, но хуже для Kafka / streaming.

Причина:

* Parquet эффективен, когда накоплен файл с большим количеством строк;
* streaming обрабатывает события по мере поступления;
* для окон и агрегатов часто нужны все атрибуты одной строки сразу;
* в Kafka удобнее передавать row-based-сообщения.

Поэтому:

```text
Kafka / streaming / RAW → Avro
Аналитическое хранение / архив / lakehouse → Parquet
DWH-слои Greenplum → разложенные колонки в таблицах
```

---

## 32. Почему Streamhouse здесь не лучший вариант

Streamhouse может казаться современным вариантом, но в данной задаче он проигрывает по требованиям.

Причины:

* историчность сложнее;
* поддержка дороже;
* много streaming + CDC;
* задача в основном batch T-1;
* аналитики знают только SQL;
* эффективность важнее технологической новизны;
* потребуется больше кода во Flink;
* чистый SQL не всегда закроет обработку.

Вывод: для этой задачи лучше классический DWH с ограниченной streaming-веткой.

## 35. Вопросы, которые могут задать на интервью

### Почему Flink, а не Spark?

Потому что Spark больше ориентирован на micro-batch, а Flink лучше подходит для настоящей потоковой обработки с низкой latency.

---

### Почему Kafka нужна между компонентами?

Kafka снижает связность компонентов, выступает буфером, позволяет независимо масштабировать потребителей и даёт универсальный интерфейс интеграции.

---

### Почему не сделать один большой Flink-монолит?

Монолит может дать меньшую latency, но усложняет релизы, тестирование, масштабирование и поддержку. Лучше декомпозировать по крупным этапам с разным профилем нагрузки.

---

### Почему не разбить всё на микросервисы?

Потому что избыточная декомпозиция создаёт overhead на сеть, сериализацию, Kafka topics, мониторинг и эксплуатацию. Нужно искать баланс.

---

### Почему Parquet для агрегатов?

Потому что агрегаты аналитические, часто читаются по части колонок, а Parquet — колоночный формат с хорошим сжатием и широкой поддержкой.

---

### Почему Avro для Kafka?

Потому что Kafka работает с сообщениями, а Avro — row-based бинарный формат со схемой и schema evolution.

---

### Почему Greenplum для DWH?

Потому что требования указывают на классический SQL-oriented DWH: 100 ТБ, T-1, SQL-аналитики, MPP, горизонтальное масштабирование и управляемая модель данных.

---

### Почему не Streamhouse?

Потому что задача в основном batch, нужна историчность, SQL-only пользователи и эффективная поддержка. Streamhouse был бы сложнее и дороже.

## 37. Краткое резюме лекции

В лекции разобраны две архитектурные задачи.

Первая задача — real-time сбор кликов из мобильного приложения. Главный вывод: для потоковой обработки лучше использовать Flink, но не делать одну огромную job. Нужно декомпозировать обработку по крупным этапам, учитывать CPU/RAM-профиль нагрузки, Kafka partitions, overhead сети и требования к latency. Для аналитического хранения агрегатов лучше использовать Parquet, потому что он колоночный и хорошо подходит для чтения отдельных колонок.

Вторая задача — построение единого DWH для рыночных данных. Здесь требования больше похожи на классический DWH: batch T-1, SQL-аналитики, 100 ТБ, историчность, витрины, банковская тайна. Поэтому основой архитектуры логично выбрать Greenplum, построить слои RAW / ODS / DDS / DataMart, использовать Data Vault для модели данных, Kafka + Avro для входного слоя, Flink для ограниченного real-time, ClickHouse для быстрого report layer и S3 + Iceberg / HDFS для архивного хранения.

Главный методологический вывод: на system design-интервью важно не просто назвать технологии, а связать каждое решение с требованиями, объяснить альтернативы, показать минусы своего варианта и предложить способы их нивелировать.
